# Intern 项目规范

本文件只维护开发与 AI 协作规范；产品定位、目录职责、技术选型、整体方案和验收要求统一维护在 [prd.md](prd.md)，不在此重复。

## PRD 遵循与变更约束

- 开发前必须阅读 [prd.md](prd.md)，按其中的产品范围、职责边界、已定选型、安全约束及验收要求实施。
- PRD 中的“推荐”“暂定”“待确认”和“未实测”不等于已采纳、已实现或已验证；不得擅自扩大支持范围或把调研结论当成生产可用性证明。
- 涉及整体方案、范围、技术选型或验收标准的变更，必须在当前仓库对应 Issue 中记录分析与结论，并同步更新 `prd.md`；未经明确决策，不得静默替换已定方案。
- Issue 记录具体工作的背景、分析、步骤、进展与交付；PRD 记录汇总后的产品要求和整体方案。PR 和辅助文档链接相应依据，不另建互相矛盾的方案副本。
- 发现实现、Issue 与 PRD 不一致时，先明确差异和依据，再协调更新，不以单处旧描述掩盖冲突。

## 组件复用与实现约束

- 缺少组件时，先搜索并评估成熟的开源组件，不重复实现已有可靠方案。
- 引入依赖前核实维护状态、许可证、目标版本兼容性与实际运行条件。
- 参考实现仅供借鉴，不能绕过 PRD 已确定的选型；复用代码须遵守原项目的许可与声明要求。

## 分支协作

- CLI 与 Web 分别在各自独立分支开发，各自实现各自的功能。
- 分支具体名称未指定，沿用仓库现有约定，不自行强制命名。
- 涉及 `base/` 的共享变更，应明确对 CLI、Web 的接口影响并协调合入，避免两条产品分支产生不兼容的共享实现。
- 未被要求时，不因本规范自动创建、切换或合并分支。

## 提交与提交前检查

- 每完成一个独立的小功能或小业务即提交一次；不得积攒多个业务后一次性大提交。
- 一个提交只解决一个明确问题，相关实现与必要测试一并提交；不混入无关文件或其他人的改动。
- commit message 使用一句简短概括，沿用 `feat:`、`fix:`、`docs:`、`chore:` 等现有前缀；需要关联 Issue 时在同一行附 `(#N)`，不堆叠长篇说明。
- 涉及业务逻辑代码变更时，提交前必须完成 build、test 和 lint；lint 使用项目配置的 `golangci-lint`，不能用 `go vet` 替代，也不能降低规则或跳过失败检查。
- 纯文档、注释、提交规范等不涉及业务逻辑的变更，不执行 build/test/lint；检查范围应与本次改动相符。
- 提交前按功能明确暂存路径，检查通过后及时提交。默认不创建/切换分支、不推送，除非用户明确要求。

## 开发追踪：以 GitHub Issue 为主

- 开发追踪（trace）以当前 GitHub 仓库的 Issue 为主要记录入口。实现、问题修复和方案调整应关联对应 Issue，持续更新分析、执行进展和验收结果。
- 本地任务清单、调研文档与 PR 是辅助材料，应链接回对应 Issue，不替代 Issue 中的核心记录。
- 每个 Issue 必须包含以下内容；尚未完成的分析或验证应明确标记状态，不得用推测冒充结论：

| 内容 | 要求 |
| --- | --- |
| 背景 | 说明需求或问题的来源、当前状态及相关上下文。 |
| 解决什么问题 | 明确目标、影响范围与不包含的内容，避免范围含糊或持续膨胀。 |
| 问题分析结果 | 记录调查证据、原因或约束、方案比较与结论，并链接相关代码、文档或实验结果。 |
| 根据结果采取的步骤 | 根据分析结论列出可执行步骤、依赖关系和进展；方案变化时同步更新原因与步骤。 |
| 验收标准 | 给出可观察、可验证的完成条件及验证方式，不能仅以“代码已写完”作为验收。 |
| 最终交付物 | 列明实际交付的代码/PR、文档、迁移或其他产物及其链接，附验收结果与验证证据。 |

- Issue 过大、包含多个可独立交付的目标时，必须拆成多个 sub-issue 分别分析、实施和验收；不能仅在大 Issue 中堆积步骤代替拆分。
- 父 Issue 记录总体背景、目标、拆分关系、依赖和整体验收标准；每个 sub-issue 同样遵守上述内容要求，并明确自己的范围、验收标准和交付物。
- 分支、提交与 PR 应按仓库现有约定关联 Issue。跨 CLI、Web、base 的工作通过父/子 Issue 明确协作边界，避免各分支重复实现或遗漏共享依赖。
- 关闭 Issue 前，逐项记录验收结果和最终交付物；未满足验收标准时不得标记完成。父 Issue 还须核对相关 sub-issue 的完成情况及整体交付结果。
