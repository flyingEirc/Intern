# 文档维护规范

## 文档职责与阅读入口

- 根 `README.md` 面向使用者：产品解决什么问题、当前可用能力、如何上手、限制与文档入口。
- 根 `AGENTS.md` / `CLAUDE.md` 只维护“要看什么 → 去哪里看”的任务索引，核心约束正文进入 `docs/`。修改必读入口时保持两者指向一致。
- `docs/roadmap/` 维护功能路线与 PRD：产品范围、阶段目标、依赖、选型决策、状态和验收边界。
- `docs/workflow/issue.md` / `pr.md` 维护跟踪与提交流程；具体背景、分析、执行进度、验收和交付以 GitHub Issue 为主。
- `docs/guide/` 维护开发、质量与文档规范。目录职责和必读列表汇总到 [docs/README.md](../README.md)。
- 根 `prd.md` 仅保留兼容入口，不再复制整体方案；旧章节引用在迁入的路线中保留对应编号。

## Roadmap 命名与内容

每个路线 Markdown 文件命名为 **`产品功能名称-YYYY-MM-DD.md`**，例如 `数据库备份与恢复-2026-10-17.md`。日期使用该路线文档建立或形成阶段决策的日期，不因日常修订反复改名；实验和交付另记实际日期。

路线至少描述背景/目标、功能范围与非目标、阶段与依赖、技术决策、验收条件、当前状态和对应 Issue。没有明确排期就不要虚构完成日期；计划不是承诺，推荐不是已采纳，完成代码不是完成验收。

日常进展更新现有文档和 Issue。新的独立功能或重大阶段决策可新增文档，但必须在目录和旧文档标明关系：补充、替代哪些部分、何时生效、依据哪个 Issue。不能仅凭文件日期最新就认定覆盖原决策。

## 变更与一致性

1. 整体方案、范围、选型和验收标准变更，先在对应 Issue 记录分析与明确结论，再同步适用路线。Issue、实现与文档冲突时先说明差异和证据，再协调更新。
2. 同一规则只维护一份正文，其他入口使用相对链接。PR 与辅助材料链接回 Issue 和路线，不另立矛盾方案。
3. README 只呈现有依据的能力，明确区分已实现、已验证和后续目标。历史记录注明时点，不能因移动文档而把历史实验更新为本次验证。
4. 命令示例对照当前入口、配置和工作目录。链接以当前文件为基准；路线中的源码路径和 shell 命令明确以 Intern 项目根为基准。
5. 新增核心文档更新 `docs/README.md`，新增必读要求更新 AI 入口。迁移时保留清晰跳转，检查原相对链接与章节引用。
6. `docs/` 下的核心 Markdown 和两个 AI 入口必须纳入 Git，不依赖个人本地忽略例外。证据只提交脱敏且必要的文件。

## 文档交付检查

- 阅读全部修改内容，对照旧规则确认没有丢失强制约束或扩大支持范围。
- 检查本地 Markdown 链接目标、章节引用、命令与配置字段；`git diff --check` 无空白问题。
- 用 `git status` / `git check-ignore` 确认核心文档会入库；按明确路径暂存并检查 `git diff --cached`。
- 按 [Issue 流程](../workflow/issue.md) 记录交付效果、检查结果、提交 SHA、harness 与模型；纯文档不运行 build/test/lint，不宣称业务重新验收。
