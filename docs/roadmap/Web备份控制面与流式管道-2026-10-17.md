## 1. 范围

### 1.1 首版包含

| 能力 | 说明 |
| --- | --- |
| 物理全量 | `xtrabackup --backup --stream=xbstream`，流式经 zstd → Tink AES-128-GCM → 备份仓库 |
| 物理增量 | 基于父备份 `to_lsn` 的页增量，可选 page tracking 加速 |
| 备份链管理 | 链 ID、父子关系、LSN 连续性、来源世代与工具版本校验 |
| 调度 | 每个策略两条 cron：全量 cron + 增量 cron；手动触发；取消 |
| 备份仓库 | **FTP / FTPS 运维备份服务器（首选）**；本地 Docker 卷（次选） |
| 隔离恢复 | 选择恢复点 → 计划 → 认证解包到工作根 → 按链 prepare → 导出隔离 datadir |
| 恢复演练 | 在工作根启动临时 mysqld 做只读校验，结果单独记录 |
| 控制面 | 用户 / 会话 / 三角色、数据源与仓库凭据加密、运行日志、审计 |

### 1.2 首版明确不包含

- **binlog 归档与 PITR**。路线第 12 节要求物理能力的验收包含“全量 + 至少两个增量 + binlog 实际恢复”，因此首版**不能宣称完整物理 PITR**；界面上 PITR 显示为“不可用：未实现 binlog 归档”。binlog 作为同一条链的下一阶段。
- K8s / Helm 部署、跨主机执行 agent（作为后续形态，见第 2.5 节）。
- Web 中的 mysqldump 逻辑链（CLI 保留现有实现，暂停扩展）。
- 控制面多副本 / HA、多租户项目隔离。
- 自动替换生产 datadir。首版只导出隔离的已 prepare 目录，切换由运维手工完成。
- S3 / SFTP 等其他仓库后端；矩阵外的 MySQL / PXB 版本组合；非 Linux 宿主机。

## 2. 部署模型：Docker 单宿主机

### 2.1 拓扑

XtraBackup 直接读取 InnoDB 数据文件，必须能访问源实例的 datadir（路线 4.1）。MySQL 以 Docker 服务运行、datadir 在持久卷上时，**Intern 容器部署在同一台 Docker 宿主机上、挂载同一个卷即可读取 datadir**，不需要额外的 agent。

```text
┌──────────────────────────── Docker 宿主机（Linux）────────────────────────────┐
│ mysql 容器（mysql:8.4.x）                                                     │
│   卷 mysql-data → /var/lib/mysql      卷 mysql-run → /var/run/mysqld（socket） │
│                     │ 只读                        │                            │
│ intern 容器（intern:<ver>-mysql8.4：intern + PXB 8.4 + mysqld 8.4）            │
│   /var/lib/mysql:ro  ← mysql-data（与 MySQL 容器相同路径）                     │
│   /var/run/mysqld    ← mysql-run（通过 socket 连接）                           │
│   /var/lib/intern/metadata  ← 卷 intern-metadata（SQLite）                     │
│   /var/lib/intern/work      ← 卷 intern-work（恢复解包、prepare、演练）        │
│   /var/lib/intern/backups   ← 卷 intern-backups（仅在使用本地仓库时）          │
│   /var/lib/intern/export    ← 宿主机目录（恢复导出）                           │
│   /run/secrets/intern_kek   ← Compose file secret（KEK，0600）                 │
│   :8080 ◄── 内网浏览器（经反向代理或内置 TLS）                                 │
└───────────────────────────────────┬──────────────────────────────────────────┘
                                    │ FTPS（首选）
                                    ▼
                        运维统一备份服务器（只存密文）
```

### 2.2 与 MySQL 容器对接的要点

| 要点 | 做法 | 依据 / 待验证 |
| --- | --- | --- |
| datadir 路径 | 挂载到与 MySQL 容器**相同的路径**（`/var/lib/mysql`），并始终显式传 `--datadir=<数据源配置的路径>` | 同一宿主机上有多个 MySQL 容器时，各自的 `@@datadir` 都是 `/var/lib/mysql`，必须按数据源配置区分挂载点 |
| 卷归属校验 | 读取挂载目录下 `auto.cnf` 的 `server-uuid`，与连接得到的 `@@server_uuid` 比对，不一致即拒绝 | 防止把 A 实例的卷当成 B 实例备份；不需要额外权限 |
| 只读挂载 | datadir 卷以 `:ro` 挂载 | xtrabackup 备份阶段不应写 datadir；路线 4.1 注明需实测，P2 必须验证 |
| 连接方式 | 共享 socket 卷，账号使用 `'intern_bkp'@'localhost'` | 走 Docker 网络 TCP 时账号 host 是容器 IP，授权范围更宽；socket 更简单、更窄 |
| 运行身份 | Intern 容器 `user:` 设为能读 datadir 的 UID/GID（官方 mysql 镜像中 mysql 用户为 999，落地时核实） | datadir 文件通常为 mysql 属主、0640 / 0750 |
| 版本对齐 | Intern 镜像按 MySQL 次版本打标签（如 `-mysql8.4`），内置对应 PXB 与 mysqld；启动和每次运行前对照版本矩阵 | PXB 必须与服务器版本匹配（第 3 节） |
| 资源隔离 | Compose 中为 intern 设置 `cpus`、`mem_limit`、`blkio_config.weight`；备份参数 `--throttle`、`--parallel` | 与生产 MySQL 同宿主机，避免抢占 IO |
| 停止与升级 | `restart: unless-stopped`，`stop_grace_period` 足够让运行中的任务按取消语义收尾；每个 metadata 卷只允许一个 intern 容器 | 单调度所有者；本地卷上 flock 可靠 |

### 2.3 #9 存储职责在 Docker 下的对应

| 职责（详细方案 6.2.1） | Docker 形态 |
| --- | --- |
| metadata | 命名卷 `intern-metadata`：SQLite（控制面 + catalog + checkpoints 原文 + 清理账本），不放任何备份载荷或工作文件 |
| 备份仓库 backups | **首选 FTP 服务器**；次选命名卷 `intern-backups`（`.pending-*` 与最终目录同文件系统） |
| work 工作根 | 命名卷 `intern-work`：xtrabackup 临时目录、lsndir、恢复解包、prepare、演练；容量按“最大一条完整链展开大小 × 恢复并发”预算 |
| keys | Compose file secret（非 swarm 模式下是宿主机文件的 bind mount，是普通文件而不是符号链接），宿主机文件 0600、属主为容器运行 UID，满足现有 KEK 读取器的要求；落地时实测 |
| 恢复导出 | 宿主机目录 bind mount，供运维用新的 MySQL 容器挂载（第 5.2 节） |

values / 环境变量 / 配置文件只保存部署参数（监听地址、路径、secret 位置）；数据源、策略、仓库配置等业务数据只存在 SQLite 中，升级镜像不覆盖（#9）。

### 2.4 镜像与许可

- Intern 镜像内置 `xtrabackup`、`xbstream`（备份与 prepare）和与源同版本的 `mysqld`（演练）。
- 镜像携带 PXB / MySQL 二进制属于分发行为，需要满足 GPLv2 义务（路线第 10 节）：许可证文本、源码提供安排、第三方声明。
- 推荐基于固定摘要的基础镜像安装固定版本的 PXB 与 mysqld 最小包，不在运行时下载二进制。

### 2.5 后续形态（不在首版实现）

MySQL 不在同一 Docker 宿主机，或者部署迁到 K8s / Helm 时，Intern 读不到 datadir，需要“控制面 + 执行 agent”：agent 与 MySQL 同机（sidecar 或 systemd），只执行 xtrabackup 并通过 HTTPS 把流上传给控制面，控制面负责压缩、加密、发布和恢复。首版代码在 `internal/physical` 中把“执行 xtrabackup 并产出 xbstream”收敛为一个接口，便于以后接入 agent，但不提前实现协议。

## 3. 版本准入与预检

### 3.1 版本矩阵

- 矩阵以数据形式内嵌（`//go:embed compat.json`），每条记录包含：服务器发行版（MySQL / Percona Server）、服务器版本范围、PXB 版本范围、平台、`verified` 标记和对应的证据 Issue。
- 首批只放 **MySQL 8.4.x + PXB 8.4.0-x / Linux amd64**（路线 4.1 的优先组合）。8.0 已 EOL，不作为默认组合。PXB 9.7 在 2026-10-17 已有官方文档页，但路线检索时只有 rc 版本，GA 状态需要重新核实后才能考虑加入。
- 版本解析使用 `github.com/hashicorp/go-version`，不比较字符串前缀。矩阵外的组合一律拒绝，禁止使用 `--no-server-version-check`。
- 备份时把服务器版本、PXB 版本写入清单；**prepare 使用的 PXB 主次版本必须与备份时一致**，否则拒绝恢复。

### 3.2 数据源预检（创建数据源和每次运行前执行）

| 检查 | 方法 | 失败处理 |
| --- | --- | --- |
| 服务器身份 | `SELECT @@server_uuid, @@version, @@version_comment, @@datadir, @@innodb_page_size` | 记录为来源世代；`server_uuid` 变化时增量拒绝，要求新全量 |
| 卷归属 | 挂载路径下 `auto.cnf` 的 `server-uuid` 与 `@@server_uuid` 一致 | 拒绝：挂错了卷 |
| 版本组合 | 服务器版本 + `xtrabackup --version` 对照矩阵 | 拒绝运行 |
| 账号权限 | `SHOW GRANTS` 解析，并实际查询 `performance_schema.log_status` | 列出缺失项，给出授权模板 |
| datadir 可读 | 以容器运行身份 `os.Stat` + 打开测试（不读内容） | 提示 UID/GID 或挂载配置错误 |
| 非 InnoDB 表 | `information_schema.tables` 中用户库 `engine <> 'InnoDB'` | 警告：这些表每次都全量复制，并需要更强的锁 |
| 表空间加密 | `performance_schema.keyring_component_status`、`information_schema.innodb_tablespaces` 的 encryption 标志 | 已使用加密但未配置 keyring 备份材料时，拒绝启用策略（路线 4.4） |
| 空间 | `golang.org/x/sys/unix.Statfs` 检查 work（和本地仓库） | 低于阈值时拒绝 |
| 仓库可写 | FTP：登录、建目录、上传并删除 `.intern-probe`；本地：同样的写删测试 | 拒绝启用策略 |
| page tracking | 查询 `mysql.component` 中 `component_mysqlbackup` | 未安装时提示，可选启用 |

备份账号授权模板（来源：Percona 官方文档，2026-10-17 经 Context7 查询；仍需按实际版本核对）：

```sql
CREATE USER 'intern_bkp'@'localhost' IDENTIFIED BY '<secret>';
GRANT BACKUP_ADMIN, PROCESS, RELOAD, LOCK TABLES, REPLICATION CLIENT ON *.* TO 'intern_bkp'@'localhost';
GRANT SELECT ON performance_schema.log_status TO 'intern_bkp'@'localhost';
GRANT SELECT ON performance_schema.keyring_component_status TO 'intern_bkp'@'localhost';
GRANT SELECT ON performance_schema.replication_group_members TO 'intern_bkp'@'localhost';
```

## 4. 备份流程

### 4.1 全量

```text
xtrabackup --defaults-extra-file=<work>/run-<id>/client.cnf   # 0600 临时凭据，必须是第一个参数
           --backup --stream=xbstream
           --socket=/var/run/mysqld/mysqld.sock
           --datadir=<数据源 datadir 挂载路径>
           --target-dir=<work>/run-<id>/xb                     # 流式模式下只存放少量临时文件
           --extra-lsndir=<work>/run-<id>/lsn                  # 另存 xtrabackup_checkpoints / xtrabackup_info
           --parallel=<N> [--page-tracking] [--throttle=<IOPS>]
   stdout ──> tap(计数/进度) ──> zstd ──> Tink StreamingAEAD ──> tap(密文 SHA-256) ──> Sink（FTP 或本地）
   stderr ──> 有界环形缓冲 + 行解析 ──> 脱敏 ──> run_logs / SSE
```

进程正常退出后：

1. 检查退出码为 0，并且 stderr 末尾出现 `completed OK!`（辅助判据，主判据是退出码）。
2. 读取 `lsn/xtrabackup_checkpoints`：要求 `backup_type = full-backuped`，解析 `from_lsn`、`to_lsn`、`last_lsn`。
3. 读取 `xtrabackup_info`（工具版本、服务器版本、binlog 位置等）。**这些文件的原始字节**连同解析结果写入清单和 SQLite（路线 4.2）；不硬编码各版本都会生成同样的文件，实际生成什么就保存什么。
4. 所有 writer 按顺序 Close 后提交 Sink → 写认证清单 → SQLite 事务标记 `completed` → 删除 `run-<id>` 工作目录。

与路线 4.2 的关系：路线推荐首版先落盘完整原生目录，再统一压缩加密，并注明“如改为 xbstream 直传，需要重新验证检查点持久化与失败收尾”。本方案选择直传，因此**第 13 节的验收必须覆盖这两项**。直传的收益是 work 卷不需要容纳整份备份。

### 4.2 增量

```text
xtrabackup … --backup --stream=xbstream
           --incremental-basedir=<work>/run-<id>/parent    # 从 SQLite 写出的父备份 checkpoints
           --extra-lsndir=<work>/run-<id>/lsn …
```

- 父备份的 checkpoints 只有几百字节，原文保存在 metadata 的 SQLite 中，运行前写入工作目录作为 `--incremental-basedir`，因此增量不需要下载父备份本体。另一种写法是 `--incremental-lsn=<parent.to_lsn>`，落地时按实际版本的 `xtrabackup --help` 二选一。
- 增量完成后校验：`backup_type = incremental`，且 `from_lsn == parent.to_lsn`。不满足时不发布。
- 下列情况拒绝增量，要求新的全量：父备份未 completed 或已被清理；`server_uuid` 变化；服务器或 PXB 主次版本变化；链长度达到 `max_chain_length`；父备份所在仓库不可读；策略的仓库已更换（一条链只在一个仓库内）。
- page tracking：全量和增量都加 `--page-tracking`，避免扫描全部页。它依赖 `component_mysqlbackup` 和 BACKUP_ADMIN；首版作为策略选项，默认关闭，验证后再考虑默认开启。

### 4.3 对生产库的影响控制

| 风险 | 控制手段 |
| --- | --- |
| DDL 阻塞 | PXB 8.x 默认用 `LOCK INSTANCE FOR BACKUP` 阻止备份期间的 DDL；界面提示“备份期间 DDL 会等待”。`--lock-ddl` 的具体取值按版本核实后再暴露 |
| 非 InnoDB 表 | 预检警告；这些表会在锁内复制 |
| IO / CPU 压力 | `--throttle`、`--parallel`、zstd 并发度作为策略参数；Compose 层限制 `cpus` 与 `blkio` 权重 |
| redo 被覆盖 | 直传时 FTP 带宽会限制 xtrabackup 的读取速度；写入高峰期的长备份可能追不上 redo。建议配置 `innodb_redo_log_archive_dirs`（路线 4.4），并监控备份时长与吞吐；带宽不足时改用“本地暂存再复制到 FTP”（第 8.4 节） |
| 同机资源争用 | 每台宿主机默认并发 1，同一数据源的全量与增量互斥，同时到期时全量优先 |

### 4.4 制品布局

每个备份生成三个文件，**清单最后写**：

```text
<仓库根>/<instance_id>/<source_id>/<chain_id>/<seq:04d>-<backup_id>/payload.xbs.zst.tink
<仓库根>/<instance_id>/<source_id>/<chain_id>/<seq:04d>-<backup_id>/envelope.json   # 加密 keyset 与 AAD（沿用 internal/artifact v1）
<仓库根>/<instance_id>/<source_id>/<chain_id>/<seq:04d>-<backup_id>/manifest.json   # AEAD 保护：checkpoints 原文、LSN、版本、SHA-256、父 ID
```

- `instance_id` 是每个 Intern 部署的唯一标识。运维备份服务器由多个团队或实例共用，Intern 只在自己的前缀下列目录、写入和删除。
- 发布判据是 SQLite 中的 `completed` 记录；没有清单的目录视为未发布或孤儿，由清理账本回收。备份索引存仓库内相对路径，不存绝对路径。

## 5. 恢复流程

### 5.1 计划（只读，默认动作）

1. 选择恢复点 B，从 catalog 取出链 `full → inc1 → … → B`。
2. 校验：每一环 `from_lsn == 父.to_lsn`、同一 chain_id、同一来源世代；仓库中所有文件存在且大小一致（FTP 用 `SIZE`）；镜像内 PXB 主次版本与备份时一致；keyring 材料可用（如果需要）。
3. 估算空间：各环展开大小之和 × 安全系数，对照 work 卷的 `Statfs`；导出时还要对照导出目录。
4. 输出计划：链清单、恢复点 LSN、所需空间、导出位置、风险提示（不会自动替换生产 datadir）。

### 5.2 执行（`admin` 角色 + 二次输入密码确认）

```text
（<restore> = <work>/restore-<restore_id>，0700）
for 每一环 i（按顺序）:
    仓库读取（FTP Retr / 本地文件）──> Tink 解密 ──> zstd 解压 ──> 限长 ──> stdin: xbstream -x -C <restore>/<i> --parallel=N
    以 Go 侧 stdin 拷贝错误为准：读到经过认证的 EOF 才算这一环完整；xbstream 退出码为 0 不代表完整

xtrabackup --prepare --apply-log-only --target-dir=<restore>/0
xtrabackup --prepare --apply-log-only --target-dir=<restore>/0 --incremental-dir=<restore>/1   # 中间各环
xtrabackup --prepare                  --target-dir=<restore>/0 --incremental-dir=<restore>/k   # 最后一环
（只有全量时：xtrabackup --prepare --target-dir=<restore>/0）
最后一次 prepare 成功后：rename <restore>/0 → <restore>/data
```

- 物理恢复**可以安全地流式解包**：解包目标是隔离的工作目录，不是任何正在运行的 datadir。任何一环认证失败就删除整个工作目录，不进入 prepare，满足“认证通过之前不写目标”。
- FTP 下载中断时可以用 `RetrFrom(offset)` 续传：续传的是同一份不可变的密文，最终仍由 Tink 认证（路线 5.2 允许对相同字节续传）。
- 每次恢复都从不可变的归档重新解包；同一工作目录不重复 prepare（路线 4.3）。`--use-memory` 作为恢复参数暴露。
- **导出**：把 `<restore>/data` 复制到导出目录 `<export>/<restore_id>/data`，并设置为 mysql 镜像的 UID/GID。运维可以直接用新容器启动验证或替换：`docker run -v <export>/<restore_id>/data:/var/lib/mysql mysql:8.4.x`。界面说明替换生产实例前需要停库、核对 `auto.cnf` 与配置。

### 5.3 恢复演练（验证）

```text
mysqld --no-defaults --datadir=<restore>/data --socket=<restore>/mysqld.sock
       --skip-networking --skip-replica-start --pid-file=… --log-error=…
→ 驱动 ping 就绪 → 只读校验 → mysqladmin shutdown → 记录结果
```

- 校验内容：能够启动；系统表可读；各用户库表数量与行数统计；对选定表执行 `CHECK TABLE`；用户在策略中配置的只读校验 SQL（例如 `SELECT max(id) FROM orders`），与备份时记录的值对比。
- 使用镜像内与源同版本的 mysqld；不监听网络、不启动复制。演练会对 `<restore>/data` 做一次干净的启动和关闭；需要导出时先导出再演练，或在结果页注明。
- 结果写入 `restores.verify_*` 字段。**backup completed 不等于恢复已验证**（路线 7.1），界面分开展示。

## 6. 流式管道 `internal/pipeline`

### 6.1 接口

```go
// Source 把数据推入 w；必须等待外部工具退出，并把工具失败、取消作为错误返回。
type Source interface {
	Run(ctx context.Context, w io.Writer) error
}

// Stage 包装下游 next，返回新的上游 writer；Close 只冲刷本节，不关闭 next。
type Stage func(next io.Writer) (io.WriteCloser, error)

// Sink 是唯一提交点：Commit 前对象不可见；Abort 幂等，可在任意状态调用。
type Sink interface {
	io.Writer
	Commit(ctx context.Context) (Receipt, error)
	Abort() error
}

func Run(ctx context.Context, src Source, stages []Stage, sink Sink) (Receipt, error)
```

`Run` 的语义：从 Sink 反向构建链；`src.Run` 返回后按“上游 → 下游”顺序 Close（计数 → zstd → 加密 → 摘要）；任一错误调用 `sink.Abort()`；全部成功才 `Commit`。ctx 取消导致的 EOF 一律视为失败。

推荐同步 writer 链而不是“每节一个 goroutine + `io.Pipe`”：zstd、Tink、hash 本身就是 writer 包装器，串起来就有背压，关闭顺序确定。只有 SDK 要求 `io.Reader` 的 Sink 才在内部用一个 pipe——FTP 的 `Stor(path, io.Reader)` 正是这种情况（第 8.2 节）。Databasus（`vendor/databasus/.../create_backup_uc.go:234-321`）为了回收 pipe 和后台写入用了多个 channel，这正是路线第 8 节指出容易漏掉 Close / 上传错误的写法。

### 6.2 XtraBackup Source 草图

```go
type XtrabackupSource struct {
	Binary, DefaultsFile, Socket, DataDir, TargetDir, LSNDir string
	Parallel                                                 int
	ParentLSNDir                                             string    // 为空表示全量
	Stderr                                                   io.Writer // 有界 + 脱敏
}

func (s *XtrabackupSource) Run(ctx context.Context, w io.Writer) error {
	args := []string{"--defaults-extra-file=" + s.DefaultsFile, "--backup", "--stream=xbstream",
		"--socket=" + s.Socket, "--datadir=" + s.DataDir,
		"--target-dir=" + s.TargetDir, "--extra-lsndir=" + s.LSNDir, "--parallel=" + strconv.Itoa(s.Parallel)}
	if s.ParentLSNDir != "" {
		args = append(args, "--incremental-basedir="+s.ParentLSNDir)
	}
	cmd := exec.CommandContext(ctx, s.Binary, args...)
	cmd.Stdout, cmd.Stderr = w, s.Stderr
	cmd.Cancel = func() error { return cmd.Process.Signal(syscall.SIGTERM) } // 先温和终止
	cmd.WaitDelay = 30 * time.Second                                         // 超时后由 os/exec 强杀并关闭管道
	configureProcess(cmd) // 复用 internal/backup/process_linux.go：Setpgid + Pdeathsig
	return cmd.Run()
}
```

- `cmd.Stdout` 是普通 writer 时，os/exec 内部拷贝；下游写失败会结束拷贝并关闭读端，子进程随后收到 EPIPE。Pipeline 同时在出错时 cancel ctx，保证进程尽快退出、错误分类一致。落地时用故障注入测试验证。
- 凭据通过 `--defaults-extra-file` 临时文件传递（沿用现有 `internal/backup` 的凭据文件机制），不放在命令行参数里。

## 7. 调度与执行

- **策略**：`full_cron`、`incremental_cron`、`timezone`、`max_chain_length`、`repository_id` 和性能参数。前端提交规范化的表达式；后端用 `cron.ParseStandard` 校验，并提供 `POST /api/v1/schedules/preview` 返回未来 5 次触发时间。
- **调度器**：`robfig/cron/v3`（路线已定，v3.0.1 自 2020 年未发版，只用它解析表达式、计算 `Next`）。触发循环自建，以 SQLite 的 `next_full_at` / `next_incremental_at` 为准。`go-co-op/gocron/v2`（v2.22.0）更活跃，但任务状态在内存中，仍需自建持久化，因此不作首选。
- **统一队列**：cron 与手动触发都向 `runs` 插入记录，幂等键为 `policy_id:kind:scheduled_at`（手动触发使用 `Idempotency-Key` 请求头），由 Worker 用 `UPDATE … RETURNING` 认领。手动触发接口返回 `202 {run_id}`。
- **规则**：同时到期时全量优先；错过的触发合并为一次；同一数据源串行；宿主机全局并发默认 1；恢复工作目录排他。
- **启动恢复**：容器重启时，遗留的 `running` 运行标记为 `failed(interrupted)`；work 中的 `run-*` / `restore-*` 目录与仓库中未发布的文件按清理账本回收（6.2.1）；进程组残留由 Pdeathsig 保证退出。
- **取消**：写入 `cancel_requested` 并调用该运行的 `CancelFunc`，管道按失败语义收尾。容器收到 SIGTERM 时对所有运行执行同样的取消。
- 状态沿用路线 7.1：`queued → running → finalizing → completed`，异常进入 `failed / canceled`。

## 8. 备份仓库：FTP 优先，本地次之

### 8.1 统一接口

`internal/storage` 中每种仓库实现 `Sink`（写入并提交）、`Open`（读取，支持从偏移继续）、`Size`、`List`（只列本实例前缀）、`Delete`。首版实现 `ftp` 与 `local` 两种。

### 8.2 FTP / FTPS（首选）

组件：`github.com/jlaffaye/ftp` v0.2.4（ISC），API 已对照 v0.2.4 源码核实：`Dial` + `DialWithExplicitTLS` / `DialWithTLS` / `DialWithTimeout` / `DialWithContext`（仅作用于建连）、`Stor`、`Rename`、`FileSize`、`MakeDir`、`Delete`、`RemoveDirRecur`、`Retr`、`RetrFrom`、`Response.SetDeadline`、`List`、`NoOp`。

| 设计点 | 做法 |
| --- | --- |
| 传输安全 | 默认**显式 FTPS**（`AUTH TLS`，`DialWithExplicitTLS`）；也支持隐式 FTPS（990 端口，`DialWithTLS`）；校验服务器证书，可配置内网 CA，`MinVersion` TLS 1.2，不提供跳过校验的开关 |
| 明文 FTP | 备份内容在离开容器前已加密，明文 FTP 不会泄露数据内容，但**会泄露 FTP 账号密码**。只有管理员在仓库配置中显式勾选“允许明文 FTP”才可使用，界面常驻风险提示并写审计 |
| 被动模式 | 使用 EPSV / PASV；保持库的默认行为——忽略服务端在 PASV 中返回的 IP、改用控制连接的地址（`DialWithTrustPasvIP` 默认 false），在 NAT 环境中更稳 |
| 连接使用 | `ServerConn` 不是并发安全的，每次传输使用独立连接；长时间传输结束后再在同一连接上执行 SIZE / RENAME |
| 写入与提交 | Sink 内部用 `io.Pipe`，后台 goroutine 执行 `Stor(<name>.part, pr)`。`Write` 写入 pipe；`Commit`：关闭 pipe → 等待 `Stor` 返回成功 → `FileSize(<name>.part)` 等于已写字节数 → `Rename` 为正式文件名 |
| 放弃与清理 | `Abort`：`pw.CloseWithError` → 等待 `Stor` 返回 → `Delete(<name>.part)`；删除失败则记入 `pending_deletions`，由后台重试 |
| 必须用临时名的原因 | 源码 `ftp.go` 中 `StorFrom` 在 reader 出错时只是关闭数据连接；在服务端看来与正常传输结束相同，可能保留一个被截断的文件并回复成功。所以绝不能直接写正式文件名，必须“临时名 + 大小核对 + rename” |
| 发布顺序 | payload → envelope → manifest，各自走“`.part` → rename”；manifest 最后 rename，随后 SQLite 标记 `completed` |
| 续传 | 上传**不续传**：加密流无法从中间续写，失败后整次重来（路线 5.2）；下载可以用 `RetrFrom` 续传相同的字节 |
| 空间与权限 | 552（超出配额）、550（权限）等错误分类为“仓库空间不足 / 权限不足”；策略启用前执行 `.intern-probe` 写删测试 |
| 实例隔离 | 首次使用时在 `<仓库根>/<instance_id>/` 写入 `.intern-instance` 标记；标记属于其他实例时拒绝使用，防止两套 Intern 写入同一前缀 |
| 完整性 | FTP 没有标准的校验和命令（`HASH` / `XCRC` 都是非标准扩展），不依赖服务端校验。上传后核对大小；另提供“仓库巡检”任务定期下载、核对 SHA-256 并完成 Tink 认证（建议每周，可配置） |
| 删除 | 只通过 `pending_deletions` 删除本实例前缀下的整条链目录（`RemoveDirRecur`），不触碰其他路径 |

### 8.3 本地（次选）

- Docker 命名卷 `intern-backups`，由现有 `internal/fsutil` 实现：写入 `.pending-<id>/` → fsync → 整体 rename 到最终目录 → fsync 父目录（6.2.1 的同文件系统发布语义）；目录 0700。
- 界面提示：本地仓库与源库在同一台宿主机上，**不能防御宿主机或磁盘故障**，只适合作为加速恢复的副本或测试环境。

### 8.4 “FTP 优先于本地”的落地方式（待决策）

| 模式 | 行为 | 评估 |
| --- | --- | --- |
| **A. 每个策略选一个仓库，默认 FTP（推荐首版）** | 新建策略时默认选中 FTP 仓库；需要时可改为本地 | 简单、链不跨仓库；FTP 不可用时运行失败并告警，不会悄悄改写到本地 |
| B. FTP 失败时自动回退到本地 | 同一条链可能一部分在 FTP、一部分在本地 | 恢复需要同时读取两处，运维以为备份都在备份服务器上，实际不是；不推荐 |
| C. 本地暂存 + 复制到 FTP | 先写本地仓库，再由 `replicate` 运行把密文原样上传到 FTP 并核对 SHA-256；本地按保留策略清理 | FTP 带宽低于备份产生速度时最稳，本地还能加速恢复；需要额外的本地空间和复制逻辑，建议作为第二步 |

多个目的地不用 `io.MultiWriter` 同时写：一个慢目的地会拖住整条链，一个失败会让全部失败。

### 8.5 保留

**保留以整条链为单位**（路线 7.3）：保留最近 N 条完整链或 D 天内的链；只有比它新的完整链 completed 之后，旧链才整体进入 `pending_deletions`；永远不删除链的中间环；被恢复引用的链加 pin。首版先实现“只读展示 + 手动删除整条链”，自动保留放在后续阶段。

## 9. 控制面：鉴权、权限、凭据、日志

| 关注点 | 方案 |
| --- | --- |
| 会话 | `scs/v2` 服务端会话，`LoadAndSave` 包住 Gin engine。**Store 用 sqlc 自行实现**（接口只有 Find / Commit / Delete）：官方 `sqlite3store` 的生产代码只依赖 `database/sql`，但它的 go.mod 会把 CGO 的 `mattn/go-sqlite3` 带进依赖图，而且自有迁移更容易纳入 goose |
| Cookie | `HttpOnly`、`Secure`、`SameSite=Lax`；登录后 `RenewToken`；空闲超时 + 绝对超时 |
| 为什么不用 JWT | 同源 SPA；服务端会话可以立即吊销 |
| 密码 | `golang.org/x/crypto/argon2` 的 argon2id，参数编码进哈希串 |
| CSRF | 标准库 `http.CrossOriginProtection`（Go 1.25+），包在 Gin 外层 |
| 登录限流 | `golang.org/x/time/rate`，按 IP + 用户名 |
| 初始管理员 | `docker compose exec intern intern user create-admin` |
| 权限 | 固定三角色：`admin`（用户、仓库、恢复执行、删除链）、`operator`（数据源、策略、手动备份）、`viewer`（只读）；`RequirePermission` 中间件。内网使用不等于免鉴权；暂不引入 Casbin |
| 凭据 | 数据源密码、FTP 密码用 Tink AEAD 加密后存入 `*_ciphertext`，AAD 为 `表:行ID:字段`；KEK 来自 Compose secret；API 只写不读，响应中返回 `has_secret: true` |
| 审计 | Gin 中间件：变更类请求完成后写 `audit_logs`，不记录 secret；cron 运行以 `system` 作为操作者，通过运行钩子写入；启用明文 FTP 单独审计 |
| 任务日志 | 带 `run_id` 的 slog Handler 批量写 `run_logs`，同时广播给 SSE；xtrabackup 的 stderr 逐行脱敏后写入，单次运行设上限 |
| 指标与健康 | `prometheus/client_golang`：最近成功时间、耗时、字节数、上传吞吐、失败次数（按数据源）；`/healthz`、`/readyz`；Compose `healthcheck` 使用 `/healthz` |
| JSON | 自有 `render.JSON`，使用 `encoding/json/v2` 编码后经 `c.Data` 输出（路线 6.1 的 Gin / jsonv2 陷阱） |

不适合做成 Gin 中间件的：通知、指标、复制、保留清理、仓库巡检、任务日志。cron 触发的运行不经过 HTTP，这些放在运行生命周期事件（`OnRunStarted` / `OnProgress` / `OnRunFinished`）中处理。

## 10. 数据模型（SQLite）

驱动沿用 `modernc.org/sqlite`；连接沿用 catalog 现有的 `WAL`、`busy_timeout(5000)`、`synchronous(FULL)`、单写连接，并增加 `foreign_keys(1)`；访问层用 sqlc，迁移用 goose 嵌入。推荐单个数据库文件，放在 metadata 卷；控制面表使用独立的 goose 版本表（goose 当前版本 v3.29.0，落地前核实自定义版本表的 API）。

```text
users(id, username UNIQUE, password_hash, role, disabled, created_at, updated_at)
sessions(token PK, data BLOB, expiry)
repositories(id, name, kind CHECK IN ('ftp','local'), config_json, secret_ciphertext,
             instance_marker, allow_plaintext, created_at)       -- ftp：host、port、tls_mode、ca、base_path、username
sources(id, name, socket, datadir_path, username, secret_ciphertext,
        server_uuid, server_version, last_preflight_json, created_at)
policies(id, source_id FK, repository_id FK, full_cron, incremental_cron, timezone,
         max_chain_length, parallel, throttle, zstd_level, page_tracking, enabled,
         next_full_at, next_incremental_at, created_at)
chains(id, source_id FK, repository_id FK, server_uuid, server_version, pxb_version,
       started_at, sealed_at, pinned)
backups(id, chain_id FK, seq, parent_id, kind CHECK IN ('physical-full','physical-incremental'),
        status, from_lsn, to_lsn, last_lsn, checkpoints BLOB, xtrabackup_info BLOB,
        object_path, payload_size, payload_sha256, key_id, created_at)   -- object_path 为仓库内相对路径
runs(id, policy_id FK NULL, kind, trigger CHECK IN ('cron','manual'), idempotency_key UNIQUE,
     status, scheduled_at, started_at, finished_at, bytes_in, bytes_out, backup_id,
     error_class, error_message, cancel_requested, actor_id)
run_logs(run_id FK, seq, ts, level, message, PRIMARY KEY(run_id, seq))
restores(id, backup_id FK, status, plan_json, work_dir, export_path, requested_by,
         started_at, finished_at, verify_status, verify_result_json, error_message)
scrubs(id, repository_id FK, backup_id FK, status, checked_at, error_message)   -- 仓库巡检结果
pending_deletions(id, repository_id FK, object_path, reason, created_at, attempts, state)
audit_logs(id, ts, actor_id, action, resource_type, resource_id, ip, result, detail_json)
```

现有 `internal/catalog` 的 `jobs` 表面向逻辑链。物理链推荐新增 `chains` / `backups` 迁移，不改动旧表语义，避免影响 CLI 已有的 state 数据库；这一点在 P3 的 Issue 中说明对 CLI 的影响。

明确不引入：Databasus 的 GORM 和自研加密容器；XtraBackup 自带的 `--encrypt`、`--compress` 与 xbcloud。后三者与项目方案的对比如下（依据：Percona 官方文档，2026-10-18 经 Context7 查询；PXB 8.4 源码 `storage/innobase/xtrabackup/src/xbcrypt_common.cc`）：

| 维度 | XtraBackup 自带 | Intern 方案 |
| --- | --- | --- |
| 加密模式 | `--encrypt=AES128/192/256`，源码固定为 **AES-CTR** | Tink `AES128GCMHKDF1MB`，AES-128-GCM 分段流 |
| 防篡改 | 没有认证标签；每块只附一个不带密钥、随数据一起加密的明文哈希，只能发现错误密钥或随机损坏，CTR 可以按位改写 | 每段都有 GCM 认证标签 |
| 截断 / 重排 | 每块独立加密，源码中看不到段序号或流结束标记 | 段序号与最后一段标记参与 nonce，读到认证结尾才算完整 |
| 上下文绑定 | 没有 AAD，文件可以跨备份替换 | AAD 绑定项目、来源、制品与 codec（路线 5.3） |
| 密钥 | 原始字符串直接作为 AES 密钥，所有备份共用，没有 key ID 和轮换 | 每个制品随机数据密钥，由 KEK 包装；有 key ID，支持多键轮换 |
| 压缩 | `--compress` 按文件压缩成 `*.zst` / `*.lz4`；恢复前必须单独执行 `--decompress`，依赖系统 zstd / lz4 包，不清理原文件会占用双倍空间 | 整条流 zstd 压缩一次，恢复时在链路中直接解压后进入 `xbstream -x` |
| 上传 | xbcloud 只支持 S3 / Swift / Azure / GCS，解析**明文** xbstream，按“库/表文件.序号”切成多个 10MB 对象；没有发布语义，完整性依赖可选的 `--md5` | 外层密文；Sink 提交 / 放弃 + 清单最后写入 + SQLite 发布；FTP / 本地均适用 |

结论：xbcrypt 能防偷看，但不能证明数据完整、来源正确，也不符合 AES-128-GCM 的约束；内外两层同时开启压缩属于重复压缩；xbcloud 只接受明文流，也不支持 FTP。PXB 自带方案的主要优势是并行吞吐；若真实压测证明单条 Tink 流是瓶颈，先调 zstd 并发，再考虑把一个备份拆成多条并行加密流，不退回 xbcrypt。

## 13. 测试与验收

| 层级 | 内容 |
| --- | --- |
| 单元 | checkpoints / xtrabackup_info 解析（含异常输入）；版本矩阵；链连续性；pipeline 关闭顺序、短写、Close 失败、取消（用假 writer / 假 Sink） |
| 进程故障注入 | 假 `xtrabackup` 脚本：中途退出非零、只输出半个流、阻塞后被取消、stderr 洪泛；断言不发布、进程组被回收 |
| FTP 仓库 | 测试 FTP 容器（显式 FTPS）：上传中途断开、服务器返回 552、证书不受信任、未允许时使用明文 FTP、服务器上残留 `.part`、`.intern-instance` 属于其他实例、下载中断后续传 |
| 真实容器拓扑 | 模拟 Compose：`mysql:8.4.x` 容器 + Intern 镜像容器，共享 datadir 卷（只读）与 socket 卷，UID 对齐 + FTP 容器（xtrabackup 只能在 Linux 运行，macOS 开发也走容器） |
| 部署 | Compose 启动、容器重启 / 重建、镜像升级后数据卷与 KEK 保留；Compose secret 中 KEK 的实际读取；同一 metadata 卷启动第二个容器被拒绝 |
| 前端 | 关键页面和状态的截图或 MP4（Issue 规范要求） |

真实容器必测场景（在路线第 12 节中，除 binlog 外的部分）：

1. 全量 → DML → 增量 1 → DML → 增量 2（仓库为 FTP）；分别恢复到**增量 1**（不是最新）和增量 2，数据与对应时刻的独立快照一致；演练实例能启动并通过校验；导出目录可被新的 mysql 容器直接启动。
2. 直传特有：xtrabackup 中途被 kill、FTP 上传中断、仓库写入失败、取消 → 无 completed 记录、未发布备份的 checkpoints 不会被当作父备份、`.part` 与工作目录进入清理账本并最终被清除。
3. 拒绝路径：缺中间环、错误父备份、`from_lsn` 不连续、错误 KEK、截断或篡改的 payload、PXB 版本不一致、矩阵外版本、挂错 datadir 卷（`auto.cnf` 不匹配）、加密表空间缺 keyring、空间不足——全部在 prepare 或写导出目录之前拒绝。
4. 提前 rollback：不允许对中间环省略 `--apply-log-only`，用测试固定 prepare 参数序列。
5. 运行规则：同一 `scheduled_at` 只执行一次；重启后合并错过的触发；全量与增量互斥。
6. 本地仓库：同样执行场景 1 的备份与恢复部分，验证 `.pending-*` 同文件系统发布。
