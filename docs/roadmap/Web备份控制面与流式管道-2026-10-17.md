## 1. 范围

### 1.1 首版包含

| 能力 | 说明 |
| --- | --- |
| 物理全量 | `xtrabackup --backup --stream=xbstream`，流式经 zstd → Tink AES-128-GCM → 本地仓库 |
| 物理增量 | 基于父备份 `to_lsn` 的页增量，可选 page tracking 加速 |
| 备份链管理 | 链 ID、父子关系、LSN 连续性、来源世代与工具版本校验 |
| 调度 | 每个策略两条 cron：全量 cron + 增量 cron；手动触发；取消 |
| 本地仓库 | Docker 卷；备份在这里发布即为 completed |
| 复制到 FTP | 发布后自动把密文原样复制到运维 FTP 服务器并校验；独立记录复制状态；先明文 FTP（受控内网使用；原内网验证已随 V1 取消，见第 0 节），随后 FTPS |
| 隔离恢复 | 选择恢复点 → 计划 → 认证解包到工作根 → 按链 prepare → 导出到宿主机目录 |
| 恢复演练 | 在工作根启动临时 mysqld 做只读校验，结果单独记录 |
| 控制面 | 用户 / 会话 / 三角色、数据源与仓库凭据加密、运行日志、审计 |

### 1.2 首版明确不包含

- **binlog 归档与 PITR**。路线第 12 节要求物理能力的验收包含“全量 + 至少两个增量 + binlog 实际恢复”，因此首版**不能宣称完整物理 PITR**；界面上 PITR 显示为“不可用：未实现 binlog 归档”。
- K8s / Helm 部署、跨主机执行 agent（后续形态，见第 2.5 节）。
- Web 中的 mysqldump 逻辑链（CLI 保留现有实现，暂停扩展）。
- 控制面多副本 / HA、多租户项目隔离。
- 自动替换生产 datadir。首版只导出隔离的已 prepare 目录，切换由运维手工完成。
- S3 / SFTP 等其他仓库后端；矩阵外的 MySQL / PXB 版本组合；非 Linux 宿主机。

## 2. 部署模型：Docker 单宿主机

### 2.1 拓扑

XtraBackup 直接读取 InnoDB 数据文件，必须能访问源实例的 datadir（路线 4.1）。MySQL 以 Docker 服务运行、datadir 在持久卷上，**Intern 容器部署在同一台宿主机、挂载同一个卷即可读取 datadir**。

```text
┌──────────────────────────── Docker 宿主机（Linux）────────────────────────────┐
│ mysql 容器（mysql:8.4.x）                                                     │
│   卷 mysql-data → /var/lib/mysql      卷 mysql-run → /var/run/mysqld（socket） │
│                     │ 只读                        │                            │
│ intern 容器（intern:<ver>-mysql8.4：intern + PXB 8.4 + mysqld 8.4）            │
│   /var/lib/mysql:ro         ← mysql-data（与 MySQL 容器相同路径）              │
│   /var/run/mysqld           ← mysql-run（通过 socket 连接）                    │
│   /var/lib/intern/metadata  ← 卷 intern-metadata（SQLite）                     │
│   /var/lib/intern/backups   ← 卷 intern-backups（本地仓库，主写入）            │
│   /var/lib/intern/work      ← 卷 intern-work（运行临时目录、恢复、演练）       │
│   /var/lib/intern/export    ← 宿主机目录（恢复导出）                           │
│   /run/secrets/intern_kek   ← Compose file secret（KEK，0600）                 │
│   :8080 ◄── 内网浏览器（经反向代理或内置 TLS）                                 │
└───────────────────────────────────┬──────────────────────────────────────────┘
                                    │ 复制已发布的密文：FTP（受控内网使用）/ FTPS
                                    ▼
                        运维统一备份服务器（只存密文）
```

### 2.2 与 MySQL 容器对接的要点

| 要点 | 做法 | 依据 / 待验证 |
| --- | --- | --- |
| datadir 路径 | 挂载到与 MySQL 容器**相同的路径**，并始终显式传 `--datadir=<数据源配置的路径>` | 同一宿主机有多个 MySQL 容器时，各自 `@@datadir` 都是 `/var/lib/mysql`，必须按数据源区分挂载点 |
| 卷归属校验 | 读取挂载目录下 `auto.cnf` 的 `server-uuid`，与 `@@server_uuid` 比对，不一致即拒绝 | 防止把 A 实例的卷当成 B 实例备份 |
| 只读挂载 | datadir 卷以 `:ro` 挂载 | xtrabackup 备份阶段不应写 datadir；路线 4.1 注明需实测，P2 必须验证 |
| 连接方式 | 共享 socket 卷，账号使用 `'intern_bkp'@'localhost'` | 走 Docker 网络 TCP 时账号 host 是容器 IP，授权范围更宽 |
| 运行身份 | Intern 容器 `user:` 设为能读 datadir 的 UID/GID（官方 mysql 镜像中 mysql 用户为 999，落地时核实） | datadir 文件通常为 mysql 属主、0640 / 0750 |
| 版本对齐 | Intern 镜像按 MySQL 次版本打标签（如 `-mysql8.4`），内置对应 PXB 与 mysqld；启动和每次运行前对照版本矩阵 | 第 3 节 |
| 资源隔离 | Compose 中为 intern 设置 `cpus`、`mem_limit`、`blkio_config.weight`；备份参数 `--throttle`、`--parallel` | 与生产 MySQL 同宿主机 |
| 停止与升级 | `restart: unless-stopped`；`stop_grace_period` 足够让运行中的任务按取消语义收尾；每个 metadata 卷只允许一个 intern 容器 | 单调度所有者 |

### 2.3 #9 存储职责在 Docker 下的对应

| 职责（详细方案 6.2.1） | Docker 形态 |
| --- | --- |
| metadata | 命名卷 `intern-metadata`：SQLite（控制面 + catalog + checkpoints 原文 + 复制状态 + 清理账本），不放备份载荷或工作文件 |
| 备份仓库 backups | 命名卷 `intern-backups` 为本地主仓库（`.pending-*` 与最终目录同文件系统）；FTP 服务器为异地副本仓库 |
| work 工作根 | 命名卷 `intern-work`：xtrabackup 临时目录、lsndir、恢复解包、prepare、演练；容量按“最大一条完整链展开大小 × 恢复并发”预算 |
| keys | Compose file secret（非 swarm 模式下是宿主机文件的 bind mount，是普通文件而非符号链接）；宿主机文件 0600、属主为容器运行 UID，满足现有 KEK 读取器要求；落地时实测 |
| 恢复导出 | 宿主机目录 bind mount，供新的 mysql 容器挂载（第 5.2 节） |

部署参数（监听地址、路径、secret 位置）放在环境变量或配置文件；数据源、策略、仓库配置等业务数据只存在 SQLite 中，升级镜像不覆盖（#9）。

### 2.4 镜像与许可

- Intern 镜像内置 `xtrabackup`、`xbstream`（备份与 prepare）和与源同版本的 `mysqld`（演练）。
- 镜像携带 PXB / MySQL 二进制属于分发行为，需要满足 GPLv2 义务（路线第 10 节）：许可证文本、源码提供安排、第三方声明。
- 基于固定摘要的基础镜像安装固定版本的 PXB 与 mysqld 最小包，不在运行时下载二进制。

### 2.5 后续形态（不在首版实现）

MySQL 不在同一 Docker 宿主机，或部署迁到 K8s / Helm 时，Intern 读不到 datadir，需要“控制面 + 执行 agent”：agent 与 MySQL 同机，只执行 xtrabackup 并通过 HTTPS 把流上传给控制面。首版在 `internal/physical` 中把“执行 xtrabackup 并产出 xbstream”收敛为一个接口，便于以后接入 agent，但不提前实现协议。

## 3. 版本准入与预检

### 3.1 版本矩阵

- 矩阵以数据形式内嵌（`//go:embed compat.json`），每条记录包含：服务器发行版、服务器版本范围、PXB 版本范围、平台、`verified` 标记和对应的证据 Issue。
- 首批只放 **MySQL 8.4.x + PXB 8.4.0-x / Linux amd64**（已确认）。8.0 已 EOL；PXB 9.7 的 GA 状态需重新核实后才能考虑加入。
- 版本解析使用 `github.com/hashicorp/go-version`，不比较字符串前缀。矩阵外的组合一律拒绝，禁止使用 `--no-server-version-check`。
- 备份时把服务器版本、PXB 版本写入清单；**prepare 使用的 PXB 主次版本必须与备份时一致**，否则拒绝恢复。
- P2（#27）锁定精确 **MySQL Community 8.4.11 / PXB 8.4.0-7 / Linux amd64**，镜像摘要保存在 `internal/physical/compat.json`；候选 `8e971aa604b7bc314683ea0897afca69b14558c2` 已通过 [原生 CI](https://github.com/flyingEirc/Intern/actions/runs/39531596550)。P2 证明运行器/预检，不自动提升完整备份恢复支持声明；矩阵暂保留 `candidate / verified=false`，实际恢复和交付仍按 D/E 验收。其他版本、平台不继承本次结论。
- 当前运行器使用首参数 `--defaults-file=/proc/self/fd/4` 读取匿名 `0600` memfd，并以 `--no-login-paths` 和环境隔离排除隐式凭据覆盖；增量使用工具支持的 `--incremental-lsn`。第 4.1 / 6.2 节的磁盘凭据与生命周期草图不作为源码实现。保留的 checkpoints/info 原文来自 `--extra-lsndir`，流内 info 会另行渲染并重新采样 `backup_size`；验收分别证明 extra-lsndir 原文字节完整与流内元数据语义一致，不将两份原文假定为同一字节串。加密表空间、redo/undo 缺 keyring 拒绝；仅有可读材料仍不能启用尚无已验证传递方案的加密源。预检的非 InnoDB 枚举在最小权限下可能不完整，会明确告警，不静默扩大到全实例 SELECT；备份必要授权当前要求直接授予账号，角色继承不作为准入证明。

### 3.2 数据源预检（创建数据源和每次运行前执行）

| 检查 | 方法 | 失败处理 |
| --- | --- | --- |
| 服务器身份 | `SELECT @@server_uuid, @@version, @@version_comment, @@datadir, @@innodb_page_size` | 记录为来源世代；`server_uuid` 变化时增量拒绝，要求新全量 |
| 卷归属 | 挂载路径下 `auto.cnf` 的 `server-uuid` 与 `@@server_uuid` 一致 | 拒绝：挂错了卷 |
| 版本组合 | 服务器版本 + `xtrabackup --version` 对照矩阵 | 拒绝运行 |
| 账号权限 | `SHOW GRANTS` 解析，并实际查询 `performance_schema.log_status` | 列出缺失项，给出授权模板 |
| datadir 可读 | 以容器运行身份 `os.Stat` + 打开测试（不读内容） | 提示 UID/GID 或挂载配置错误 |
| 非 InnoDB 表 | `information_schema.tables` 中用户库 `engine <> 'InnoDB'` | 警告：这些表每次都全量复制，并需要更强的锁 |
| 表空间加密 | `performance_schema.keyring_component_status`、`information_schema.innodb_tablespaces` 的 encryption 标志 | 已使用加密但未配置 keyring 备份材料时，拒绝启用策略（路线 4.4） |
| 空间 | `golang.org/x/sys/unix.Statfs` 检查本地仓库与 work | 低于阈值时拒绝（本地仓库至少容纳一条完整链 + 一次进行中的全量） |
| 仓库可写 | 本地与 FTP 各做一次 `.intern-probe` 写删测试 | 拒绝启用策略 |
| page tracking | 查询 `mysql.component` 中 `component_mysqlbackup` | 未安装时提示，可选启用 |

备份账号授权模板（来源：Percona 官方文档，2026-10-17 经 Context7 查询；仍需按实际版本核对）：

```sql
CREATE USER 'intern_bkp'@'localhost' IDENTIFIED BY '<secret>';
GRANT BACKUP_ADMIN, PROCESS, RELOAD, LOCK TABLES, REPLICATION CLIENT ON *.* TO 'intern_bkp'@'localhost';
GRANT SELECT ON performance_schema.log_status TO 'intern_bkp'@'localhost';
GRANT SELECT ON performance_schema.keyring_component_status TO 'intern_bkp'@'localhost';
GRANT SELECT ON performance_schema.replication_group_members TO 'intern_bkp'@'localhost';
```

## 4. 备份流程

### 4.1 全量

```text
xtrabackup --defaults-extra-file=<work>/run-<id>/client.cnf   # 0600 临时凭据，必须是第一个参数
           --backup --stream=xbstream
           --socket=/var/run/mysqld/mysqld.sock
           --datadir=<数据源 datadir 挂载路径>
           --target-dir=<work>/run-<id>/xb                     # 流式模式下只存放少量临时文件
           --extra-lsndir=<work>/run-<id>/lsn                  # 另存 xtrabackup_checkpoints / xtrabackup_info
           --parallel=<N> [--page-tracking] [--throttle=<IOPS>]
   stdout ──> tap(计数/进度) ──> zstd ──> Tink StreamingAEAD ──> tap(密文 SHA-256) ──> 本地仓库 Sink
   stderr ──> 有界环形缓冲 + 行解析 ──> 脱敏 ──> run_logs / SSE
```

进程正常退出后：

1. 检查退出码为 0，并且 stderr 末尾出现 `completed OK!`（辅助判据，主判据是退出码）。
2. 读取 `lsn/xtrabackup_checkpoints`：要求 `backup_type = full-backuped`，解析 `from_lsn`、`to_lsn`、`last_lsn`。
3. 读取 `xtrabackup_info`（工具版本、服务器版本、binlog 位置等）。**这些文件的原始字节**连同解析结果写入清单和 SQLite（路线 4.2）；实际生成什么就保存什么，不硬编码文件清单。
4. 所有 writer 按顺序 Close 后提交本地 Sink → 写认证清单 → SQLite 事务标记 `completed` → 删除 `run-<id>` 工作目录 → 触发复制（第 8.3 节）。

与路线 4.2 的关系：路线推荐首版先落盘完整原生目录，再统一压缩加密，并注明“如改为 xbstream 直传，需要重新验证检查点持久化与失败收尾”。本方案以压缩加密后的流直接写入本地仓库，work 卷不需要容纳整份原生备份，因此**第 13 节的验收必须覆盖这两项**。

### 4.2 增量

```text
xtrabackup … --backup --stream=xbstream
           --incremental-basedir=<work>/run-<id>/parent    # 从 SQLite 写出的父备份 checkpoints
           --extra-lsndir=<work>/run-<id>/lsn …
```

- 父备份的 checkpoints 只有几百字节，原文保存在 SQLite 中，运行前写入工作目录作为 `--incremental-basedir`；增量不需要父备份本体，本地仓库清理掉父备份载荷也不影响后续增量。另一种写法是 `--incremental-lsn=<parent.to_lsn>`，落地时按实际版本的 `xtrabackup --help` 二选一。
- 增量完成后校验：`backup_type = incremental`，且 `from_lsn == parent.to_lsn`。不满足时不发布。
- 下列情况拒绝增量，要求新的全量：父备份未 completed；`server_uuid` 变化；服务器或 PXB 主次版本变化；链长度达到 `max_chain_length`。
- page tracking：全量和增量都加 `--page-tracking`；依赖 `component_mysqlbackup` 和 BACKUP_ADMIN，首版作为策略选项，默认关闭。

### 4.3 对生产库的影响控制

| 风险 | 控制手段 |
| --- | --- |
| DDL 阻塞 | PXB 8.x 默认用 `LOCK INSTANCE FOR BACKUP` 阻止备份期间的 DDL；界面提示“备份期间 DDL 会等待”。`--lock-ddl` 取值按版本核实后再暴露 |
| 非 InnoDB 表 | 预检警告；这些表会在锁内复制 |
| IO / CPU 压力 | `--throttle`、`--parallel`、zstd 并发度作为策略参数；Compose 层限制 `cpus` 与 `blkio` 权重 |
| redo 被覆盖 | 备份写本地磁盘，速度不受 FTP 带宽限制；写入高峰期仍建议配置 `innodb_redo_log_archive_dirs`（路线 4.4） |
| 本地仓库与 datadir 同盘 | 备份写入会与 MySQL 争用同一块磁盘的 IO；条件允许时把 `intern-backups` 放在另一块盘 |
| 同机资源争用 | 备份运行全局并发 1，同一数据源的全量与增量互斥，同时到期时全量优先；复制运行单独排队（第 7 节） |

### 4.4 制品布局（本地与 FTP 相同）

```text
<仓库根>/<instance_id>/<source_id>/<chain_id>/<seq:04d>-<backup_id>/payload.xbs.zst.tink
<仓库根>/<instance_id>/<source_id>/<chain_id>/<seq:04d>-<backup_id>/envelope.json   # 加密 keyset 与 AAD（沿用 internal/artifact v1）
<仓库根>/<instance_id>/<source_id>/<chain_id>/<seq:04d>-<backup_id>/manifest.json   # AEAD 保护：checkpoints 原文、LSN、版本、SHA-256、父 ID
```

- 两处仓库使用同一相对路径，复制就是逐文件原样拷贝。
- `instance_id` 是每个 Intern 部署的唯一标识；FTP 服务器由多个团队或实例共用，Intern 只在自己的前缀下列目录、写入和删除。
- 发布判据是 SQLite 中的记录（备份 `completed`、副本 `verified`）；没有清单的目录视为未发布或孤儿，由清理账本回收。索引只存相对路径。

## 5. 恢复流程

### 5.1 计划（只读，默认动作）

1. 选择恢复点 B，从 catalog 取出链 `full → inc1 → … → B`。
2. **选择读取来源**：每一环优先读本地仓库；本地已按保留策略清理的，读 FTP 副本（要求副本状态为 `verified`）。计划中逐环列出来源。任一环两处都不可用则拒绝。
3. 校验：每一环 `from_lsn == 父.to_lsn`、同一 chain_id、同一来源世代；所选来源中文件存在且大小一致（FTP 用 `SIZE`）；镜像内 PXB 主次版本与备份时一致；keyring 材料可用（如果需要）。
4. 估算空间：各环展开大小之和 × 安全系数，对照 work 卷与导出目录的 `Statfs`。
5. 输出计划：链清单与来源、恢复点 LSN、所需空间、导出位置、风险提示（不会自动替换生产 datadir）。

### 5.2 执行（`admin` 角色 + 二次输入密码确认）

```text
（<restore> = <work>/restore-<restore_id>，0700）
for 每一环 i（按顺序）:
    来源读取（本地文件 / FTP Retr）──> Tink 解密 ──> zstd 解压 ──> 限长 ──> stdin: xbstream -x -C <restore>/<i> --parallel=N
    以 Go 侧 stdin 拷贝错误为准：读到经过认证的 EOF 才算这一环完整；xbstream 退出码为 0 不代表完整

xtrabackup --prepare --apply-log-only --target-dir=<restore>/0
xtrabackup --prepare --apply-log-only --target-dir=<restore>/0 --incremental-dir=<restore>/1   # 中间各环
xtrabackup --prepare                  --target-dir=<restore>/0 --incremental-dir=<restore>/k   # 最后一环
（只有全量时：xtrabackup --prepare --target-dir=<restore>/0）
最后一次 prepare 成功后：rename <restore>/0 → <restore>/data
导出：复制 <restore>/data → <export>/<restore_id>/data，属主设为 mysql 镜像的 UID/GID
```

- 物理恢复**可以安全地流式解包**：解包目标是隔离的工作目录，不是任何正在运行的 datadir。任何一环认证失败就删除整个工作目录，不进入 prepare。
- FTP 下载中断时用 `RetrFrom(offset)` 续传同一份不可变密文，最终仍由 Tink 认证（路线 5.2 允许对相同字节续传）。
- 每次恢复都从不可变的归档重新解包；同一工作目录不重复 prepare（路线 4.3）。`--use-memory` 作为恢复参数暴露。
- **导出到宿主机目录（已确认）**：导出目录不存在于 metadata / backups / work 之内；导出完成后界面给出可直接使用的命令 `docker run -v <宿主机导出路径>/<restore_id>/data:/var/lib/mysql mysql:8.4.x`，并说明替换生产实例前需要停库、核对 `auto.cnf`（同一 `server-uuid` 不能与源实例同时接入复制拓扑）与配置。导出目录由运维自行清理，界面显示占用空间。

### 5.3 恢复演练（已确认包含）

```text
mysqld --no-defaults --datadir=<restore>/data --socket=<restore>/mysqld.sock
       --skip-networking --skip-replica-start --pid-file=… --log-error=…
→ 驱动 ping 就绪 → 只读校验 → mysqladmin shutdown → 记录结果
```

- 顺序：**先导出，再在工作目录副本上演练**，导出的目录保持 prepare 后的原样。
- 校验内容：能够启动；系统表可读；各用户库表数量与行数统计；对选定表执行 `CHECK TABLE`；策略中配置的只读校验 SQL（例如 `SELECT max(id) FROM orders`），与备份时记录的值对比。
- 使用镜像内与源同版本的 mysqld；不监听网络、不启动复制。
- 结果写入 `restores.verify_*` 字段。**backup completed 不等于恢复已验证**（路线 7.1），界面分开展示。

## 6. 流式管道 `internal/pipeline`

### 6.1 接口

```go
// Source 把数据推入 w；必须等待外部工具退出，并把工具失败、取消作为错误返回。
type Source interface {
	Run(ctx context.Context, w io.Writer) error
}

// Stage 包装 next；Close 只冲刷本节、不关闭 next。同一 writer 的 Write 串行，内部工作协程须在 Close 前结束。
type Stage func(next io.Writer) (io.WriteCloser, error)

// Sink 是对象提交点：Commit 成功后 Run 不因后到取消调用 Abort；失败清理必须幂等。
type Sink interface {
	io.Writer
	Commit(ctx context.Context) (Receipt, error)
	Abort() error
}

func Run(ctx context.Context, src Source, stages []Stage, sink Sink) (Receipt, error)
```

`Run` 的语义：从 Sink 反向构建链；`src.Run` 返回后按“上游 → 下游”顺序 Close（计数 → zstd → 加密 → 摘要）；提交前的错误或 `Commit` 返回错误调用 `sink.Abort()`；全部成功才 `Commit`。Source 因取消而返回的错误/EOF 一律失败。`Commit` 返回成功后直接返回 receipt，不因随后取消反向撤销（PR #26 用户确认）；对象提交不自动等同于清单与 catalog 已完成发布。同一 writer 的 `Write` 必须串行，Stage 内部协程须协调下游写并在关闭前结束；安全传递取消原因不代表 hash writer 支持并发写。

推荐同步 writer 链而不是“每节一个 goroutine + `io.Pipe`”：zstd、Tink、hash 本身就是 writer 包装器，串起来就有背压，关闭顺序确定。只有 SDK 要求 `io.Reader` 的 Sink 才在内部用一个 pipe——FTP 的 `Stor(path, io.Reader)` 属于这种情况（第 8.4 节）。复制运行也复用同一套 `Run`：Source 是本地文件读取，没有 Stage，Sink 是 FTP。Databasus（`vendor/databasus/.../create_backup_uc.go:234-321`）为回收 pipe 和后台写入用了多个 channel，这正是路线第 8 节指出容易漏掉 Close / 上传错误的写法。

### 6.2 XtraBackup Source 草图

```go
type XtrabackupSource struct {
	Binary, DefaultsFile, Socket, DataDir, TargetDir, LSNDir string
	Parallel                                                 int
	ParentLSNDir                                             string    // 为空表示全量
	Stderr                                                   io.Writer // 有界 + 脱敏
}

func (s *XtrabackupSource) Run(ctx context.Context, w io.Writer) error {
	args := []string{"--defaults-extra-file=" + s.DefaultsFile, "--backup", "--stream=xbstream",
		"--socket=" + s.Socket, "--datadir=" + s.DataDir,
		"--target-dir=" + s.TargetDir, "--extra-lsndir=" + s.LSNDir, "--parallel=" + strconv.Itoa(s.Parallel)}
	if s.ParentLSNDir != "" {
		args = append(args, "--incremental-basedir="+s.ParentLSNDir)
	}
	cmd := exec.CommandContext(ctx, s.Binary, args...)
	cmd.Stdout, cmd.Stderr = w, s.Stderr
	cmd.Cancel = func() error { return cmd.Process.Signal(syscall.SIGTERM) } // 先温和终止
	cmd.WaitDelay = 30 * time.Second                                         // 超时后由 os/exec 强杀并关闭管道
	configureProcess(cmd) // 复用 internal/backup/process_linux.go：Setpgid + Pdeathsig
	return cmd.Run()
}
```

- `cmd.Stdout` 是普通 writer 时，os/exec 内部拷贝；下游写失败会结束拷贝并关闭读端，子进程随后收到 EPIPE。Pipeline 同时在出错时 cancel ctx，保证进程尽快退出、错误分类一致。落地时用故障注入测试验证。
- 凭据通过 `--defaults-extra-file` 临时文件传递（沿用现有 `internal/backup` 的凭据文件机制），不放在命令行参数里。

## 7. 调度与执行

- **策略**：`full_cron`、`incremental_cron`、`timezone`、`max_chain_length`、本地仓库、FTP 副本仓库、本地保留参数和性能参数。前端提交规范化的表达式；后端用 `cron.ParseStandard` 校验，并提供 `POST /api/v1/schedules/preview` 返回未来 5 次触发时间。
- **调度器**：`robfig/cron/v3`（路线已定，v3.0.1 自 2020 年未发版，只用它解析表达式、计算 `Next`）。触发循环自建，以 SQLite 的 `next_full_at` / `next_incremental_at` 为准。`go-co-op/gocron/v2`（v2.22.0）任务状态在内存中，仍需自建持久化，不作首选。
- **统一队列**：cron、手动触发和复制都向 `runs` 插入记录。备份幂等键为 `policy_id:kind:scheduled_at`（手动触发使用 `Idempotency-Key` 请求头），复制幂等键为 `replicate:backup_id:repository_id`。认领使用 `UPDATE … RETURNING`；手动触发接口返回 `202 {run_id}`。
- **两条执行通道**：备份 / 恢复通道并发 1（同宿主机 IO 敏感）；复制通道并发 1，可与备份并行（主要消耗网络）。同一数据源的全量与增量互斥，同时到期时全量优先；错过的触发合并为一次。
- **复制顺序**：按备份创建顺序复制；前一个备份尚未复制成功时，后续备份排队等待，保证 FTP 上“可恢复前缀”连续。复制失败按指数退避重试（例如 1 分钟起、上限 1 小时），超过阈值告警，不影响本地备份继续进行。
- **启动恢复**：容器重启时，遗留的 `running` 运行标记为 `failed(interrupted)`；work 中的 `run-*` / `restore-*` 目录、本地 `.pending-*` 与 FTP 上的 `.part` 按清理账本回收（6.2.1）；进程组残留由 Pdeathsig 保证退出；中断的复制重新排队。
- **取消**：写入 `cancel_requested` 并调用该运行的 `CancelFunc`，管道按失败语义收尾。容器收到 SIGTERM 时对所有运行执行同样的取消。
- 状态（W4 已实现，见第 10 节）：`queued → running → completed | failed | canceled`。实际状态机没有 `finalizing`——物理链的成功提交是 `Run` 调用内部的步骤，控制面观测不到；中断记为 `failed` 且 `error_class=interrupted`。

## 8. 备份仓库：先本地，再复制到 FTP

### 8.1 模式（已确认 C）

```text
xtrabackup ─► pipeline ─► 本地仓库发布（completed） ─► 复制运行 ─► FTP 副本（uploaded → verified）
                                     │                                   │
                                     └── 本地保留：副本 verified 且超出保留范围后才清理本地载荷
```

| 状态 | 含义 | 界面展示 |
| --- | --- | --- |
| 备份 `completed` | 本地已发布，可用于恢复 | “本地可恢复” |
| 副本 `uploaded` | 三个文件都已上传并 rename，大小一致 | “已上传，待校验” |
| 副本 `verified` | 已完成校验（见第 8.3 节） | “异地已保护” |
| 副本 `failed` | 重试耗尽 | 告警：异地保护中断 |

- **RPO 的两种口径**：防误删 / 数据损坏看最近一次本地 completed；防宿主机故障看 FTP 上最近一段**连续 verified** 的链前缀。界面分别显示两项，复制积压超过阈值即告警。
- 首版不做“FTP 失败自动回退”或“同时写两处”。

### 8.2 本地仓库

- 本地仓库由 `internal/storage/local` 实现：写入 `.pending-*` → 文件/目录 fsync → 原子不覆盖 rename 到最终目录 → 父目录/根目录 fsync（6.2.1 同文件系统发布语义）；目录 0700、文件 0600。`Begin` 提前拒绝已存在目标，`Publish` 仍保留原子不覆盖检查应对竞争。取消在 rename 前检查；rename 与持久化成功后不因后来取消回滚，真实 fsync 错误仍尝试恢复 pending，回滚失败时不删除状态不确定的已发布目录。私有 pending 目录同步不占仓库命名空间锁，父目录创建/rename/相关同步仍串行化并可能阻塞读者；同一 staging 的多 sink 写仍串行，取消不能打断内核中的磁盘 I/O。
- **本地保留**：每个策略配置“本地至少保留最近 N 条完整链”（默认 1）。一条本地链只有在**全部成员副本都已 verified**，且超出保留范围时，才进入 `pending_deletions` 删除本地载荷；元数据和 checkpoints 不删除。未完成异地复制的备份绝不清理。
- 空间不足时备份失败并告警，不会删除未复制的备份来腾空间。

### 8.3 复制运行

1. Source 为本地文件读取，Sink 为 FTP（第 8.4 节），按 payload → envelope → manifest 的顺序逐个上传，各自走“`.part` → 核对大小 → rename”。
2. 上传时在读取侧同步计算 SHA-256，必须等于本地清单中记录的值（防止本地文件在复制前已损坏）。
3. 三个文件都 rename 成功后，副本标记 `uploaded`。
4. 校验：FTP 没有标准的校验和命令（`HASH` / `XCRC` 都是非标准扩展），因此采用**回读校验**——下载 payload 并计算 SHA-256、完成 Tink 认证读取，通过后标记 `verified`。首版对每个副本执行一次；网络开销大时可改为“上传后核对大小即标记 verified + 定期抽查巡检”，届时需要重新决策。
5. 定期巡检：按配置周期（建议每周）抽查或全量回读 FTP 副本，结果写入 `scrubs`，失败时把副本降级为 `failed` 并重新复制。

### 8.4 FTP 实现（先明文 FTP 供受控内网使用，随后 FTPS；内网验证已取消，见第 0 节）

组件：`github.com/jlaffaye/ftp` v0.2.4（ISC），API 已对照 v0.2.4 源码核实：`Dial` + `DialWithTimeout` / `DialWithContext`（仅作用于建连） / `DialWithExplicitTLS` / `DialWithTLS`、`Login`、`Stor`、`Rename`、`FileSize`、`MakeDir`、`Delete`、`RemoveDirRecur`、`Retr`、`RetrFrom`、`Response.SetDeadline`、`List`、`NoOp`。

| 设计点 | 做法 |
| --- | --- |
| 传输模式 | 仓库配置 `tls_mode`：`plain`（受控内网使用）、`explicit`（`AUTH TLS`，`DialWithExplicitTLS`）、`implicit`（990 端口，`DialWithTLS`）。三种使用同一套 Sink 逻辑，只有建连参数不同 |
| 明文 FTP 的边界 | 备份内容在复制前已加密并带认证，明文传输不泄露数据内容、篡改会被发现；**泄露的是 FTP 账号密码**。`plain` 需要管理员在仓库配置中显式选择，界面常驻提示，写审计；建议为 Intern 单独开一个只能访问自己目录的 FTP 账号 |
| FTPS（S2 实施） | 校验服务器证书（可配置内网 CA：仓库配置 `ftp.ca_pem`，只含 CERTIFICATE 块、≤ 256 KiB，省略时用系统信任库；主机名按 `ftp.host` 校验），`MinVersion` TLS 1.2，不提供跳过校验的开关。库在使用自定义拨号函数时不再包装连接，所以 Intern 的拨号函数自己加密：implicit 的控制连接在交给库之前完成握手，explicit 的控制连接由库在 `AUTH TLS` 后升级；数据连接一律返回未握手的 `tls.Client`，在 STOR/RETR/LIST 发出后的首次读写时握手（Pure-FTPd 只在收到传输命令后才开始数据通道 TLS，提前握手会卡到拨号超时），`tls.Conn` 握手成功前不写任何应用字节。服务器不支持 TLS、证书不受信任/主机名不符/过期时在发送 USER/PASS 之前失败，不回退明文；在受控内网作为推荐模式（原“内网验证通过后”的排期已随 V1 取消，见第 0 节） |
| 被动模式 | 使用 EPSV / PASV；保持库的默认行为——忽略服务端在 PASV 中返回的 IP、改用控制连接的地址（`DialWithTrustPasvIP` 默认 false），容器 NAT 环境更稳 |
| 连接使用 | `ServerConn` 不是并发安全的，每次传输使用独立连接；传输完成后再在同一连接上执行 SIZE / RENAME |
| 写入与提交 | Sink 内部用 `io.Pipe`，后台 goroutine 执行 `Stor(<name>.part, pr)`。`Write` 写入 pipe；`Commit`：关闭 pipe → 等待 `Stor` 成功 → `FileSize(<name>.part)` 等于已写字节数 → `Rename` 为正式文件名 |
| 放弃与清理 | `Abort`：`pw.CloseWithError` → 等待 `Stor` 返回 → `Delete(<name>.part)`；删除失败则记入 `pending_deletions` 由后台重试 |
| 必须用临时名的原因 | 源码 `ftp.go` 中 `StorFrom` 在 reader 出错时只关闭数据连接；在服务端看来与正常结束相同，可能保留被截断的文件并回复成功。绝不能直接写正式文件名 |
| 续传 | 上传不续传，失败后该文件整体重传（复制的是已有的固定字节，重传代价只是带宽）；下载可用 `RetrFrom` 续传 |
| 空间与权限 | 552（超出配额）、550（权限）等错误分类为“仓库空间不足 / 权限不足”；策略启用前执行 `.intern-probe` 写删测试 |
| 实例隔离 | 首次使用时在 `<仓库根>/<instance_id>/` 写入 `.intern-instance` 标记；标记属于其他实例时拒绝，防止两套 Intern 写入同一前缀 |
| 删除 | 只通过 `pending_deletions` 删除本实例前缀下的整条链目录（`RemoveDirRecur`）；FTP 侧保留策略按整条链计算（第 8.5 节） |

S1（#28）当前实现以 `internal/storage/ftp` 为准：

- 只接受显式 `TLSMode="plain"`，空值、explicit/implicit 在建连前拒绝。凭据仍以明文传输，须使用隔离网络与专用 chroot 账号；W3 的配置审计和前端常驻提示不在 S1 内完成。
- 对象键包含 `instance_id`；已有未标记或异实例目录拒绝接管。先以绝对字面路径 `CWD`，再无路径参数 `LIST -a`，避免空格与 `*?[]` 被当作列表模式；保留符号链接类型和隐藏标记，不采用当前 SDK 的 MLSD 未知类型回退。BasePath、InstanceID 与键分量拒绝 C0/DEL 及首尾 ASCII 空格，避免服务端将其重写成其他对象名；内部空格和通配字符仍按字面名称支持。
- `Create` 在写入前暴露唯一 `.intern-upload-<随机值>.part` 清理引用；传入的 context 覆盖整个 Sink 生命周期，R1 必须使用运行/传输级 context。STOR、数据 Close、最终响应、SIZE 全部成功后才 rename。完成点之后的取消不回滚；RNTO 回复丢失返回 `ErrCommitUncertain`，可能已发布的正式对象保留给 R1 回读认证，不能宣称不存在或 verified。FTP 不提供原子 NOREPLACE；当前仅支持单部署、单复制写入通道，不承诺远端多写者互斥。
- `Abort`/`CleanupPart` 只清理本实例临时键，失败返回包含精确相对路径的 `CleanupError` 供 R1 清理账本重试。S1 的 `Delete` 删除单个已发布对象，不擅自作保留决策；整条链删除仍需业务层的引用与状态检查。错误分类保留 `ReplyCode`，R1/W3 不应仅依赖外层 `Kind`；550 不一概等于权限不足。列表未找到名称时，字面 SIZE/CWD 成功只能否决“不存在”，不能伪造对象类型或授权读删；服务端可能限制列表条数，业务状态与清理必须使用持久 catalog 的精确对象键。
- S1 最终候选 `bbf8cab6ae315be574fd789c2f81ad90676746e8` 通过 [原生完整 CI 39888716748](https://github.com/flyingEirc/Intern/actions/runs/39888716748)：19 个真实 FTP 场景（含字面路径与服务端列表截断回归）、P2、两种 CLI 矩阵、build/race/lint 与总门禁均成功；FTP 证据制品 12473612451，事件 SHA256 `79d7645b967093dbbdcfb0ac3bbce4311b432d56fb748f1e31ce9151e3c8a479`。两路独立验收对 S1-A1–A5 无 blocker/major。服务端须开启 quotas，不能使用缺少该功能的 Alpine minimal 二进制冒充 552 验收；原生 worker 不带 race，race 覆盖来自单元层。
- 测试服务使用未修改的 Pure-FTPd 1.0.54 系统 crypt 路径，固定 musl/musl-dev 1.2.6-r3（MIT），启动时核验官方 `pure-pw` 生成的两账号均为默认 bcrypt cost 10；拒绝意外后端或弱算法回退，不手工生成 hash 或调整 rounds。包版本通过 `apk list --installed` 绑定。r3 跟随 Alpine 对 CVE-2026-107891 的安全修订；旧 r2 从在线仓库撤换会阻断重建，不允许自动放宽版本约束，构建日志保留供精确诊断。
- [原生诊断 CI 39562163372](https://github.com/flyingEirc/Intern/actions/runs/39562163372) 确认旧测试构建中 pure-pw 与 daemon 的可选 libsodium 初始化差异导致 x86 密码验证超过预算，凭据本身正确；DNS、TCP、欢迎响应正常，`-H` 不是该失败的修复。认证构建修正未改上游源码、产品存储行为或业务超时，原生对照和修复证据保存在 #28。


### 8.5 FTP 侧保留

**保留以整条链为单位**（路线 7.3）：保留最近 N 条完整链或 D 天内的链；只有比它新的完整链在 FTP 上全部 verified 之后，旧链才整体进入 `pending_deletions`；永远不删除链的中间环；被恢复引用的链加 pin。首版先实现“只读展示 + 手动删除整条链”，自动保留放在后续阶段。

## 9. 控制面：鉴权、权限、凭据、日志

| 关注点 | 方案 |
| --- | --- |
| 会话 | `scs/v2` 服务端会话，由 Gin 内的自有中间件调用 scs 的 Load / Commit / 写 Cookie：响应头写出前提交，提交失败只返回一次 500 错误体，`/healthz`、`/readyz` 不加载会话（2026-10-18 用户批准替代原“`LoadAndSave` 包住 Gin engine”：scs v2.9.0 的 `LoadAndSave` 在提交失败时会把错误体与业务响应混写，见 [#23](https://github.com/flyingEirc/Intern/issues/23)）。登出以 tombstone 记录已删除的 token，阻止在途请求的提交使其复活。**Store 用 sqlc 自行实现**（接口只有 Find / Commit / Delete）：官方 `sqlite3store` 的生产代码只依赖 `database/sql`，但它的 go.mod 会把 CGO 的 `mattn/go-sqlite3` 带进依赖图，而且自有迁移更容易纳入 goose |
| Cookie / 入口 | `HttpOnly`、`Secure`、`SameSite=Lax`；登录后 `RenewToken`；空闲超时 + 绝对超时。默认 `127.0.0.1:8080`；非回环明文必须显式 `tls_terminated_by_proxy` 且配置受信代理，否则要求本进程 TLS。代理 IP 信任不等于 TLS，明文后端仍须网络隔离 |
| 为什么不用 JWT | 同源 SPA；服务端会话可以立即吊销 |
| 密码 | `golang.org/x/crypto/argon2` 的 argon2id，参数编码进哈希串 |
| CSRF | 标准库 `http.CrossOriginProtection`（Go 1.25+），包在 Gin 外层 |
| 登录限流 | `golang.org/x/time/rate`，按 IP + 用户名；每进程 Argon2 总并发 2，匿名登录最多 1，为已登录的改密/管理保留容量；资源忙仍立即 `503` + `Retry-After`，不宣称匿名登录在攻击流量下永不受阻 |
| 初始管理员 | `docker compose exec intern intern user create-admin` |
| 权限 | 固定三角色：`admin`（用户、仓库、恢复执行、删除链）、`operator`（数据源、策略、手动备份、手动重试复制）、`viewer`（只读）；`RequirePermission` 中间件。内网使用不等于免鉴权；暂不引入 Casbin |
| 凭据 | 数据源密码、FTP 密码用 Tink AEAD 加密后存入 `*_ciphertext`，AAD 为 `表:行ID:字段`；KEK 来自 Compose secret；API 只写不读，响应中返回 `has_secret: true` |
| 审计 | 用户创建/修改/改密/角色/禁用/批量吊销和登出的数据库变更，与成功 `audit_logs` 同事务；插入成功审计失败则回滚变更（PR #26 用户确认）。失败/拒绝/CSRF及登录审计仍尽力写入，失败记录日志；避免重复成功审计，不记录 secret。Cookie 传输与改密后的 token 轮换不属于数据库原子事务。cron 与复制运行的审计仍在后续业务阶段接入；明文 FTP 选择的成功审计已由 W3 与配置变更同事务写入 |
| 任务日志 | 带 `run_id` 的 slog Handler 批量写 `run_logs`，同时广播给 SSE；xtrabackup 的 stderr 逐行脱敏后写入，单次运行设上限 |
| 指标与健康 | `prometheus/client_golang`：最近本地成功时间、最近异地 verified 时间、复制积压数量、耗时、字节数、上传吞吐、失败次数（按数据源）；`/healthz`、`/readyz`；Compose `healthcheck` 使用 `/healthz` |
| JSON | 自有 `render.JSON`，使用 `encoding/json/v2` 编码后经 `c.Data` 输出（路线 6.1 的 Gin / jsonv2 陷阱） |
| 会话失败边界 | 响应输出前的 handler 或中间件 panic 返回统一 `500`，不提交修改后的 session、不额外销毁已有会话；已输出后的 panic 只能记录错误，不能收回响应。响应缓冲上限 8 MiB，超限或 Flush/Hijack 请求拒绝为单一 `500`，不假装支持 SSE；已输出后的 Write 返回错误。该上限仅约束会话缓冲，不代表 JSON 编码或整进程的内存上限。改密事务成功但 token 轮换失败时，旧 epoch 仍须失效，用户使用新密码重新登录 |

## 10. 数据模型（SQLite，单文件，已确认）

驱动沿用 `modernc.org/sqlite`；连接沿用 catalog 现有的 `WAL`、`busy_timeout(5000)`、`synchronous(FULL)`、单写连接，并增加 `foreign_keys(1)`；访问层用 sqlc，迁移用 goose 嵌入。数据库文件放在 metadata 卷；控制面与物理链各用独立的 goose 版本表（当前固定 goose v3.26.0，`WithTableName` 已在该版本可用）。

```text

sessions(token PK, data BLOB, expiry)
repositories(id, name, kind CHECK IN ('local','ftp'), config_json, secret_ciphertext,
             tls_mode CHECK IN ('none','plain','explicit','implicit'), instance_marker, created_at)
             -- local：root；ftp：host、port、ca、base_path、username；local 的 tls_mode 为 none
sources(id, name, socket, datadir_path, username, secret_ciphertext,
        server_uuid, server_version, last_preflight_json, created_at)

backups(id, chain_id FK, seq, parent_id, kind CHECK IN ('physical-full','physical-incremental'),

     trigger CHECK IN ('cron','manual','system'), idempotency_key UNIQUE,
```

现有 `internal/catalog` 的 `jobs` 表面向逻辑链。物理链新增 `chains` / `backups` / `replicas` 迁移，不改动旧表语义，避免影响 CLI 已有的 state 数据库；这一点在 P3 的 Issue 中说明对 CLI 的影响。

P3（#29）当前实现以 `internal/physical/store`、`internal/physical/chain` 为准：

- `app/web` 打开并持有 `intern.db`（flock 与 DSN 不变），在 Web 迁移后调用 `store.Migrate` 迁移物理表，版本表为 `physical_goose_db_version`；`Ready` 与 `migrate status` 同时要求物理版本等于内嵌最新。物理表为 `chains`、`backups`、`cleanup_ledger`；`source_id` 仍是不透明文本，没有指向 `sources` 的数据库外键，删除引用由 W3 在 API 层拒绝。CLI `catalog.sqlite`/`jobs` 不变。
- 世代标识为 `server_uuid`。增量须满足：父备份 `completed` 且为该链最新成员、`server_uuid`、精确服务器版本与精确工具版本均与链一致、链长度未达上限；否则返回带 `RequiresFull` 的准入错误。链最新成员失败后该链不再接受增量，下一次须全量（保守且有意）。LSN 以十进制 TEXT 保存完整 uint64。
- 对象目录 `<instance_id>/<source_id>/<chain_id>/<seq:04d>-<backup_id>/`（全量 seq=1），成员为 `payload.bin` + `envelope.json`（流，v1 制品，manifest 为流前已知的身份信息）与 `metadata.bin` + `metadata.envelope.json`（原始 checkpoints/`--extra-lsndir` info 与流密文大小/SHA256，第二个 v1 认证制品）；同时写入 SQLite。v1 AAD 仍只绑定 format/compression/cipher/key_id/manifest 与 keyset 摘要，不宣称跨对象绑定；不另存未认证 `manifest.json`。原始 info 以 `--extra-lsndir` 为准，流内 info 的 `backup_size` 会重新采样。
- 顺序：`Begin` 同一 IMMEDIATE 事务写 running 行与 staging/workdir/object 三条清理账本行 → 建 `run-<id>` 工作目录与 `.pending-<run_id>` → 流水线 zstd→Tink→staging → 两个制品提交 → 删除并 sync 工作目录 → `Publish`（NOREPLACE）→ `Complete`（`WithoutCancel` 有界提交）。`Complete` 事务提交才是成功点，并同时删除账本行；此前任何失败都标记 failed、尽力回收并保留未完成的账本行。工作目录删除失败也不完成（宁可重备份）。`Recover` 只处理本实例、非活跃 run 的精确账本目标（`ReclaimPending`、`ReclaimPublished` 带 fsync），不做前缀扫描，幂等。
- 调用方责任（W4 接线时已落实，见下文 W4 条目）：`Run` 仍只在内部生成工作目录 id，不接受控制面的 run id；`Recover` 必须与 `Run` 由同一调度所有者串行执行；运行所用的 KEK 既要在 WorkRoot 之外，也要在该运行钉住的本地仓库根之外；`Run` 需要调用方提供本次的新鲜预检身份。

R1（#30）当前实现以 `internal/replication` 为准：

- `app/web` 在 Web 迁移和物理迁移之后调用 `replication.Migrate`，版本表为 `replication_goose_db_version`；`Ready` 与 `migrate status` 同时要求复制版本等于内嵌最新。复制表为 `replicas`、`replica_members`、`replica_parts`；`replicas.local_repository_id`（迁移 00002）是队列的配对键。幂等键为 `replicate:<backup_id>:<repository_id>`；`repository_id` 仍是不透明文本，没有指向 `repositories` 的数据库外键；W3 在删除仓库时检查副本引用。CLI `catalog.sqlite`/`jobs` 不变。
- 远端键是本地对象路径加成员名，且路径的实例前缀必须是本实例。目录仍是 `<instance_id>/<source_id>/<chain_id>/<seq:04d>-<backup_id>/`，四个成员按固定顺序上传：`payload.bin` → `envelope.json` → `metadata.bin` → `metadata.envelope.json`。只复制本地 `completed` 且 `local_present` 的密文；上传前核对 payload 与 metadata 的大小和 SHA-256。
- `uploaded` 只表示四个成员的 Commit 都已确认，此时还没有证明。`verified` 只在偏移 0 回读、SHA-256 与字节数和记录一致、两份 v1 制品用链 KEK 认证到 EOF、且清单与备份行一致之后写入；认证缺失、中断、截断或损坏不能标 verified。验证失败但四次提交已确认时保持 `uploaded`。只有 `verified` 计入异地保护点。
- RNTO 回复丢失（`ErrCommitUncertain`）把该成员记为 `uncertain` 并结束本轮。正式键不删除、不重写，本轮也不能宣称 `uploaded`。下一轮只看正式键是否存在：存在则留给回读认证，不存在才重新上传。已存在的正式键绝不覆盖。
- `replica_parts` 在写出第一个载荷字节之前记下临时键。成功 Commit 或成功 `CleanupPart` 后删行；清理失败保留该行，`Recover` 再试。`Recover` 还把中断的 `uploading` 退回 `pending`，并完成已经提交的本地删除预约。`Step` 与 `Recover` 由同一调度所有者串行调用。复制失败不阻断新的本地备份。
- 排队、FIFO 与 `Recover` 都按（本地仓库，副本仓库）对划分：队列读写以 `replicas.local_repository_id` 过滤（迁移 00002），同一个 FTP 仓库被两个本地仓库共享时是两个互不读取对方行的队列，迁移前没有该绑定的行不匹配任何复制器。配对内部严格 FIFO：前驱未 `verified`（含 `failed` / `exhausted`）时后继不得开始。这是执行侧规则；保护点的读规则不同——远端点是该源在该仓库上的副本行并集里跳过缺口的最长 verified 前缀，seq 缺口只丢弃它所在的链，不阻断后面的链（见下一条）。零值策略为基线 1 分钟、上限 1 小时、`min(BaseDelay·2^(attempts-1), MaxDelay)`、最多 10 次、`AlertAfter` 6 小时。可重试失败在次数用尽时变为 `exhausted`，之后不再自动尝试；不可重试失败为 `failed` 且 `permanent`。告警只是 `alert_since` 状态：耗尽和不可重试立即置位，其余要等首次未解决失败超过 `AlertAfter`；没有通知器。`Retry` 立即重排、尝试次数归零并保留错误码；随后达到 `verified` 时清除告警。
- `LocalPoint` 是该源最近一条、前缀全部 completed 的链上最后一个 completed 备份。`RemotePoint` 读该源在该仓库上的副本行并集（同仓库的每个（本地仓库，副本仓库）对各自的队列都计入），按链位置排序后由两条规则决定前缀在哪结束：一行存在但未 `verified` 就结束前缀；seq 缺口只丢掉它所在的整条链——该链在缺口之后的成员即使存在且未 `verified` 也一起跳过，扫描继续到下一条链。因此点是最后一条同时满足三个条件的链的最后一个成员：整链 `verified`、从 seq 1 起无缺口地存在于该仓库、且在它之前没有遇到任何非缺口链的未 `verified` 行；base 未入库的 verified 增量随整条链被跳过，永远不会成为点。缺口处本地点停在缺口之前，远端点跳过该链继续，两点都只由各自已经证明的副本决定，供 W4 分开计算 RPO。
- 保留只针对整条本地链，且不会自动执行（自动保留仍为 N2）。新的删除预约要求链未 pin、成员全部 completed、本仓库整链 verified，并且存在更新且整链 verified 的链；否则拒绝，原因为 `pinned`、`incomplete`、`unverified`、`latest` 或 `no_newer_verified`。已经提交的预约一定由 `DeleteLocalChain` 或 `Recover` 完成，之后的 pin 或其他失格不能取消它；pin 只拒绝新预约。回收只删除本地载荷目录，备份行、checkpoints 与元数据保留。

W4（#32）当前实现以 `app/web/internal/dispatch`、`app/web/internal/server` 的 SSE 路由与 `app/web/internal/store` 的 runs 表为准：

- 触发幂等：cron 键为 `policy:<id>:<kind>:<scheduled_at>`，手动触发用 `Idempotency-Key` 加请求体哈希。相同键与相同请求体重放返回原 run 的 `202`；不同请求体、或禁用策略下的新键返回 `409`。缺少 KEK、work root 或 XtraBackup 时手动触发立即返回 `503`，cron 运行仍建行并可见地失败。
- 备份通道并发 1：认领用 `UPDATE … RETURNING` 取一行，已有运行处于 `running` 时拒绝认领，因此全局同时只有一个备份，同源互斥随之成立；排队序为全量先于增量，再按 `scheduled_at`。每个数据源同时最多一个 `queued`/`running` 全量。
- 错过的触发合并：`next_*_at` 直接作为 `scheduled_at`，随后推进到 `Next(now)`，所以一个 tick 里每个策略只建一行；全量与增量同时到期时全量胜出，该次到期增量不入队。增量因需要全量而被准入拒绝后，用 `policy:<id>:full:admission:<scheduled_at>` 键补一次合并全量——键按每次尝试唯一，早先的准入全量失败不会阻止下一次。
- 运行钉住仓库对：认领语句同时把策略的 `(local, replica)` 仓库对快照进 `runs.local_repository_id` / `replica_repository_id`（迁移 00007，升级时按策略回填一次）。预检、KEK 检查、物理链与复制交接都读该快照，因此之后的 PUT 只影响下一次运行，不会把已有备份重绑到从未写入的仓库。
- 保护点：运行与复制状态 API 与 `runs`、`replicas`、物理链一致，RPO 分开查询（`GET /api/v1/sources/{id}/protection`）。远端点按仓库在“该源在该仓库上的副本行并集”里取跳过缺口的最长 verified 前缀末项：存在但未 `verified` 的行结束前缀，seq 缺口只丢掉它所在的整条链后继续下一条链；`uploaded` 永不当作 `verified`，验证时间不参与排序。
- 结构化事件：`run_logs` 增加 `data` 列（迁移 00006），`message` 仍是固定脱敏文案，`data` 承载类型化对象；SSE 只读这些行，不读进程内状态。
- SSE：`GET /api/v1/runs/{id}/events` 在首字节前完成与 JSON 路由相同的会话与 `runs:read` 检查（`401`/`403` 仍是 JSON），随后使用未缓冲的流式 writer，响应 `text/event-stream`、`no-cache`、`X-Accel-Buffering: no`。先按 `Last-Event-ID` / `after_seq` 重放 `run_logs`，再推实时事件，终止时发一个 `end` 事件并关闭；每次心跳（≤15 秒）重做会话检查（用户存在且启用、epoch 未变、权限仍在），吊销、登出或降权后发 `revoked` 并关闭；每个订阅者 256 条的有界缓冲区溢出时只丢弃该订阅者，不阻塞运行。
- 取消与停机：取消一个 `queued` 运行直接把它结束为 `canceled`；取消 `running` 运行写 `cancel_requested`（系统审计 `runs.cancel_requested`）并取消该运行的 context，成功点尚未提交时按存储的标志结束为 `canceled` 且不产生备份，已提交的成功点优先，取消不会撤销已完成的备份。容器 SIGTERM 取消运行上下文并最多等待 45 秒，超时报告错误并交给下一次启动的恢复，该运行结束为 `failed` 且 `error_class=backup_failed`；物理链执行中被 SIGKILL 的运行不会写 `completed`，下一次启动记为 `failed`/`interrupted`。

- 执行通道：恢复与备份 run 全局并发 1——`ClaimNextRun` 与恢复认领在同一写语句里同时检查两张表。状态 `queued → running → completed | failed | canceled`；`phase` 只表示运行中的实时阶段，任何终态写入都置空，真实阶段序列在 `restore_logs`；`verify_status ∈ not_requested|pending|passed|failed|not_run`，与恢复状态分开。每个终态行都写 `side_effects`（工作目录/待发布导出是否已移除、导出是否已发布），未分类失败时从文件系统观测而非默认全假。
- 取消与重启：取消 queued 直接 `canceled`；取消 running 写 `cancel_requested` 并取消上下文（注册上下文后会重读该标志，避免窗口内丢失），已发布的导出不被撤销。启动恢复先把遗留 running 的恢复记为 `failed/interrupted`，调用 `restore.Recover` 只回收该 id 的两个精确目标并写回 `side_effects`，已发布导出保留。
- 原生验收：`app/web/integration/w5_test.go` 的 `TestW5NativeContainers` 复用 P4 的 worker 镜像，经 HTTPS API 用 W4 建全量 + 两次增量并等副本 verified、删除本地载荷后计划全为 FTP，二次确认恢复增量 1（含演练）、增量 2 与全量，由 harness 在新的 `mysql:8.4.11` 容器上启动导出并比对快照；另证明确认失败/限流/`plan_changed`/幂等、双向互斥、queued 与 prepare 中取消、serve 进程在 prepare 中被 SIGKILL 后的重启回收、FTP 载荷缺失时 `409 source_unavailable`、未配置恢复依赖时 `503`。CI：GitHub Actions 的 `container-restore-api` job 用 `verify-w5-evidence.sh` 校验，`w5-gate-cases.sh` 在 quality-fast 自测。

明确不引入：Databasus 的 GORM 和自研加密容器；XtraBackup 自带的 `--encrypt`、`--compress` 与 xbcloud。后三者与项目方案的对比如下（依据：Percona 官方文档，2026-10-18 经 Context7 查询；PXB 8.4 源码 `storage/innobase/xtrabackup/src/xbcrypt_common.cc`）：

| 维度 | XtraBackup 自带 | Intern 方案 |
| --- | --- | --- |
| 加密模式 | `--encrypt=AES128/192/256`，源码固定为 **AES-CTR** | Tink `AES128GCMHKDF1MB`，AES-128-GCM 分段流 |
| 防篡改 | 没有认证标签；每块只附一个不带密钥、随数据一起加密的明文哈希，只能发现错误密钥或随机损坏，CTR 可以按位改写 | 每段都有 GCM 认证标签 |
| 截断 / 重排 | 每块独立加密，源码中看不到段序号或流结束标记 | 段序号与最后一段标记参与 nonce，读到认证结尾才算完整 |
| 上下文绑定 | 没有 AAD，文件可以跨备份替换 | AAD 绑定项目、来源、制品与 codec（路线 5.3） |
| 密钥 | 原始字符串直接作为 AES 密钥，所有备份共用，没有 key ID 和轮换 | 每个制品随机数据密钥，由 KEK 包装；有 key ID，支持多键轮换 |
| 压缩 | `--compress` 按文件压缩成 `*.zst` / `*.lz4`；恢复前必须单独执行 `--decompress`，依赖系统 zstd / lz4 包，不清理原文件会占用双倍空间 | 整条流 zstd 压缩一次，恢复时在链路中直接解压后进入 `xbstream -x` |
| 上传 | xbcloud 只支持 S3 / Swift / Azure / GCS，解析**明文** xbstream，按“库/表文件.序号”切成多个 10MB 对象；没有发布语义，完整性依赖可选的 `--md5` | 外层密文；本地发布 + 复制到 FTP，副本单独校验与记录 |

结论：xbcrypt 能防偷看，但不能证明数据完整、来源正确，也不符合 AES-128-GCM 的约束；内外两层同时开启压缩属于重复压缩；xbcloud 只接受明文流，也不支持 FTP。PXB 自带方案的主要优势是并行吞吐；若真实压测证明单条 Tink 流是瓶颈，先调 zstd 并发，再考虑把一个备份拆成多条并行加密流，不退回 xbcrypt。

1. 全量 → DML → 增量 1 → DML → 增量 2；分别恢复到**增量 1**（不是最新）和增量 2，数据与对应时刻的独立快照一致；导出目录可被新的 mysql 容器直接启动；演练实例能启动并通过校验。
2. 从 FTP 恢复：删除本地载荷（模拟本地保留清理或宿主机故障），只从 FTP 副本完成场景 1 的恢复。

4. 拒绝路径：缺中间环、错误父备份、`from_lsn` 不连续、错误 KEK、截断或篡改的 payload（本地与 FTP 各一次）、PXB 版本不一致、矩阵外版本、挂错 datadir 卷（`auto.cnf` 不匹配）、加密表空间缺 keyring、空间不足——全部在 prepare 或写导出目录之前拒绝。
5. 提前 rollback：不允许对中间环省略 `--apply-log-only`，用测试固定 prepare 参数序列。
6. 运行规则：同一 `scheduled_at` 只执行一次；重启后合并错过的触发；全量与增量互斥；复制按顺序进行，前一个未成功时后续不越过。

场景归属按上述用户决定执行：阶段 C/P3、R1 验收备份、复制与副本完整性部分；场景 1 的实际恢复以及场景 2 的仅 FTP 恢复均保留给阶段 D/P4，仍须分别恢复增量 1 和增量 2 并比对独立快照。阶段 C 不因尚未实施 P4 而形成循环结项依赖，也不把副本认证成功写成恢复成功；阶段 E 原计划的内网恢复（V1）已于 2026-11-05 取消，仅 FTP 副本的恢复由 D/P4 与每次涉及代码或配置的推送及每日定时运行的容器 CI 覆盖。
