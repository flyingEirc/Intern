## 1. 背景与目标

用户在 2026-10-17 提出 Web 路线的六点设想，本文逐条给出工程评估、修正与可落地结构：

| # | 用户设想 | 评估结论 |
| --- | --- | --- |
| 1 | 备份是流转 io 流的 pipeline，参考 Databasus；cron 自动调度 + HTTP 手动调度 | 采纳。两种触发**汇入同一个持久化运行队列**，不各自直接调用引擎（第 4 节）。 |
| 2 | 任务设置由前端规定，backend 只负责执行 | **修正**：前端负责编辑和展示，后端是唯一事实来源，负责校验、持久化和调度计算。浏览器关闭后 cron 仍需由后端触发（第 4.1 节）。 |
| 3 | 使用 SQLite 存储用户、权限、数据源等信息 | 采纳，并与路线 6.2 一致：单实例 Web 用 SQLite + `modernc.org/sqlite`，不外推到多实例（第 7 节）。 |
| 4 | 用户权限、登录鉴权、操作/任务日志、上云（FTP/SFTP/S3）尽量用成熟 Go 库 | 采纳，选型见第 6、8 节。 |
| 5 | 数据库 → 备份流 → zstd → 加密 → 本地/远程存储，每段一节“水管” | 采纳 pipeline 心智模型；实现上推荐**同步 writer 装饰链**，而非每节一个 goroutine + `io.Pipe`（第 3 节）。 |
| 6 | 非核心业务作为 Gin 中间件 | **部分采纳**：HTTP 横切关注点（鉴权、审计、访问日志）用中间件；cron 触发的任务不经过 Gin，上传、通知、任务日志应作为 pipeline 阶段或运行生命周期钩子（第 5 节）。 |

目标：形成首版 Web 的产品概念、模块边界、数据模型与可拆分的实施顺序，供 #18 决策后拆成独立子 Issue。

## 2. 产品概念

Intern Web 是**单实例、自托管的 MySQL 备份控制面**：一个 Go 二进制同时提供 HTTP API、内嵌前端和后台调度执行器。

```text
浏览器 SPA ──HTTPS──> Gin API ──> 控制面服务（校验 / 持久化 / 权限）
                                      │
               cron 触发器 ──┐        ▼
                             ├──> runs 队列（SQLite，幂等键）──> Worker 池 ──> Pipeline
               手动触发 ─────┘                                        │
                                                                      ▼
                                 Source(mysqldump…) → zstd → Tink AEAD → Sink(local/S3/SFTP/FTP)
                                                                      │
                                         发布清单 → catalog 事务标记 completed → 事件钩子（通知、日志、复制）
```

核心实体（用户可见的名词）：

| 实体 | 含义 | 首版是否需要 |
| --- | --- | --- |
| 用户 / 角色 | 登录身份与固定权限集 | 是 |
| 数据源 Source | 被备份的 MySQL 连接；密码加密保存、只写不回显 | 是 |
| 存储 Storage | 备份目的地：local、S3 兼容；SFTP/FTP 后置 | local + S3 |
| 备份策略 Policy | 数据源 × 存储 × 备份类型 × cron × 时区 × 压缩/加密 | 是 |
| 运行 Run | 一次执行记录：触发来源、状态、字节数、错误分类、日志 | 是 |
| 备份 Backup | 已发布的制品与链关系（沿用 `internal/catalog`） | 是 |
| 恢复 Restore | 恢复计划、目标确认与执行结果 | 阶段 D |
| 审计 Audit | 谁在何时对什么资源做了什么 | 是 |

首版非目标：多实例/HA、多租户项目隔离、XtraBackup 物理链、Agent 远程执行、任意时间点 PITR、自动保留删除。路线中这些仍是后续目标，不在此提前宣称。

## 3. 流式管道（核心）

### 3.1 推荐模型：Source 推送 + writer 装饰链 + 可提交 Sink

每节水管的接口推荐如下（示意，最终以实现 Issue 为准）：

```go
package pipeline // 建议位置：internal/pipeline

// Source 把数据推入 w；必须等待外部工具退出，并把工具失败、取消作为错误返回。
type Source interface {
	Run(ctx context.Context, w io.Writer) error
}

// Stage 包装下游 next，返回新的上游 writer。
// Close 只冲刷本节剩余数据，不关闭 next；关闭顺序由 Run 统一负责。
type Stage func(next io.Writer) (io.WriteCloser, error)

// Sink 是唯一提交点：Commit 前对象不可被恢复选择器看见；Abort 可在任意状态调用且幂等。
type Sink interface {
	io.Writer
	Commit(ctx context.Context) (Receipt, error)
	Abort() error
}

func Run(ctx context.Context, src Source, stages []Stage, sink Sink) (Receipt, error)
```

`Run` 的固定语义：

1. 从 Sink 反向构建链：`sink ← encrypt ← zstd ← taps`，链头交给 `src.Run`。
2. Source 返回后按**上游到下游**依次 Close（zstd → 加密 → 计数/摘要），任一错误立即 `sink.Abort()`。
3. 全部成功才 `sink.Commit()`；之后由业务层写认证清单、在 SQLite 事务中标记 completed。对象存在不等于备份已发布（路线 7.2）。
4. ctx 取消导致的 EOF 一律视为失败，不发布、不推进水位。

为什么推荐同步装饰链而非“每节一个 goroutine + io.Pipe”：

- zstd、Tink、hash、计数本身就是 `io.Writer` 包装器，串成一条调用链即可，天然有背压，不需要额外协程。
- 错误传播和关闭顺序是确定的；Databasus 的实现（`vendor/databasus/.../create_backup_uc.go:234-321`）需要多个 channel 和 select 来回收 pipe 与后台写入，正是路线第 8 节指出容易漏掉 Close/上传错误的地方。
- 只有 SDK 要求 `io.Reader` 的 Sink 才在 Sink 内部用一个 `io.Pipe` 适配；`gocloud.dev/blob` 的 Writer 本身就是 writer，无需适配。
- 用 `golang.org/x/sync/errgroup` 只协调确实并发的部分：工具进程、stderr 收集和 Sink 后台上传。

心智模型仍然是“水管”：Source 是水源，Stage 是串联的过滤器，Sink 是水箱，`Commit` 就是关上水箱阀门、贴上封条。

### 3.2 每节水管的职责

| 节 | 实现 | 说明 |
| --- | --- | --- |
| Source: logical-full | `mysqldump … --single-transaction --source-data=2` 的 stdout | 现有 `runTool` 已接受 `io.Writer`，可直接接到链头。快照坐标改由 **tap 阶段扫描前 8 MiB** 获得，不再整份落盘后回读。 |
| Source: binlog | `mysqlbinlog --raw` 先写到受控 spool，再以 tar 流推出 | `--raw` 只能写文件，这一节**允许先落盘**；pipeline 抽象不承诺零磁盘。 |
| Source: physical（后续） | `xtrabackup --backup --stream=xbstream --extra-lsndir=…` | 需要源机数据目录访问权限，Web 必须与 MySQL 同机或者后续引入 Agent；增量用 `--incremental-lsn`，读取 `--extra-lsndir` 中的 checkpoints。首版不做。 |
| Tap: 坐标 / 计数 / 进度 | 透传 writer | 计数供进度 SSE；坐标扫描有上限，超过即判定失败。 |
| Stage: 压缩 | `klauspost/compress/zstd` | 固定先压缩后加密，并发与级别作为配置，不照搬 Databasus 的固定值。 |
| Stage: 加密 | Tink `AES128GCMHKDF1MB` Streaming AEAD | AAD 绑定路线 5.3 规定的不可变字段；现有 `internal/artifact` 抽出 `encode` 中的 writer 构造即可复用。 |
| Tap: 密文摘要 | `sha256` + 计数 | 写入清单；复制和恢复前核对。 |
| Sink | local / S3 / SFTP / FTP（第 6 节） | 每种实现都提供“临时对象 → 提交”语义。 |

### 3.3 必须正视的两点

- **恢复不能端到端流式直写目标**。路线要求“完整认证和范围检查通过后才能写目标”，而 Tink 只有读到经过认证的 EOF 才能确认完整。因此恢复是两遍：第一遍 `Sink 读取 → 解密 → 解压 → io.Discard` 验证摘要、认证与展开上限；第二遍再导入。远程存储的取舍是下载两次，或者把已认证密文暂存在受控目录（现有实现采用暂存）。
- **多目的地不要用 `io.MultiWriter` 扇出**。一个慢目的地会拖住整条链，一个失败会让全部失败。推荐每个策略只写一个主存储，再由独立的 `replicate` 运行把密文原样复制到副存储并核对 SHA-256，不重新加密。

### 3.4 对现有代码的影响

- `internal/backup/full.go` 当前流程是：落盘 `dump.sql` → 回读坐标 → 计算摘要 → tar → `artifact.Write`。改为流式属于 `internal/` 的行为变更，需要在单独的 Issue 中说明对 CLI 的影响，并重跑真实容器矩阵（#2–#4 门禁）。
- `internal/artifact.Write` 目前直接写 `payload.bin` 与 `envelope.json` 两个本地文件。引入 Sink 后，envelope 也需要经过同一个 Sink 写出，并在 payload 之后提交，否则远程存储上会出现缺 envelope 的“半个备份”。

## 4. 调度与执行

### 4.1 前端定义、后端执行的边界

- 前端提供友好的编辑器（每天 HH:MM、每 N 分钟、自定义表达式），提交规范化后的 `{cron_expr, timezone}`。
- 后端用 `cron.ParseStandard` + `time.LoadLocation` 校验，拒绝秒级或非法表达式，并提供 `POST /api/v1/schedules/preview` 返回未来 5 次触发时间，供前端展示。
- 策略、`next_run_at` 与运行状态全部持久化在 SQLite；前端只读取和发起变更请求，不参与触发计算。

### 4.2 统一运行队列

```text
cron 循环：SELECT 到期策略 → 事务内 INSERT runs(idempotency_key = policy_id:scheduled_at) ON CONFLICT DO NOTHING
          → UPDATE policies.next_run_at = schedule.Next(now)
手动触发：POST /api/v1/policies/{id}/runs（Idempotency-Key 请求头）→ INSERT runs → 202 {run_id}
Worker  ：UPDATE runs SET status='running' … RETURNING 认领 → 执行 Pipeline → 终态
```

- **调度器选型**：继续使用路线已定的 `robfig/cron/v3`，**只用作表达式解析与 `Next` 计算**；触发循环自己实现并以 SQLite 中的 `next_run_at` 为准。这样重启不丢计划，`(schedule_id, scheduled_at)` 幂等，也和现有 `internal/schedule` 的思路一致。robfig/cron 多年未发版，但解析器功能稳定、范围小。`go-co-op/gocron/v2` 维护更活跃，支持 singleton 与运行时更新任务，不过它的任务状态保存在内存里，仍需自建持久化，因此不作为首选。
- **错过触发**：重启后若 `next_run_at` 早于当前时间，合并为一次运行，不逐个补跑（与现有 CLI 的“合并错过的间隔”一致）。
- **并发控制**：同一数据源同一时刻只运行一个任务（全量优先于 binlog）；全局 Worker 信号量限制总并发；恢复目标使用排他锁。单进程内用 map + mutex 即可，但运行状态以数据库认领结果为准。
- **启动恢复**：启动时遗留的 `running` 运行标记为 `failed(interrupted)`，并交给现有清理账本回收孤儿对象。
- **取消**：API 写入 `cancel_requested` 并调用内存中对应运行的 `context.CancelFunc`；Pipeline 按失败语义收尾。

运行状态沿用路线 7.1：`queued → running → finalizing → completed`，异常进入 `failed / canceled`。

## 5. 横切关注点：中间件与运行钩子

| 关注点 | 位置 | 推荐实现 |
| --- | --- | --- |
| panic 恢复、请求 ID、访问日志 | Gin 中间件 | `gin.Recovery` 或自定义；访问日志接 slog，不记录请求体 |
| 会话加载/保存 | `http.Handler` 外层包住 Gin | `scs.LoadAndSave(engine)` |
| CSRF / 跨源 | `http.Handler` 外层 | Go 1.25+ 标准库 `http.CrossOriginProtection`（基于 `Sec-Fetch-Site`/`Origin`）+ SameSite Cookie |
| 认证、权限 | Gin 路由组中间件 | `RequireAuth`、`RequirePermission(perm)` |
| 操作审计 | Gin 中间件 | 对变更类方法在 handler 完成后写 `audit_logs`（actor、action、资源、结果、IP），不记录 secret 字段 |
| 请求体大小、登录限流 | Gin 中间件 | `http.MaxBytesReader`；`golang.org/x/time/rate` 按 IP + 用户名限流 |
| 任务日志、进度 | **Pipeline / 运行钩子** | 带 `run_id` 的 slog Handler 批量写 `run_logs`，同时广播给 SSE 订阅者 |
| 通知、指标、复制、保留清理 | **运行生命周期事件** | `OnRunFinished` 等事件分发给订阅者；cron 运行不经过 HTTP，不能放在 Gin 中间件里 |
| 上云上传 | **Sink**（pipeline 末节） | 第 6 节 |

Gin 与 jsonv2：路线 6.1 已指出 Gin 默认 codec 使用 `encoding/json`。推荐自有 `render.JSON(c, status, v)`，用 `encoding/json/v2` 编码后通过 `c.Data` 输出，绑定同样使用 `json.Unmarshal`。

## 6. 存储（上云）

统一放在 `internal/storage`，每种后端实现 `Sink`（写）与 `Open`（读，供恢复和复制使用）：

| 后端 | 推荐库 | 提交语义与注意点 |
| --- | --- | --- |
| local | 现有 `internal/fsutil`（或 `gocloud.dev/blob/fileblob`） | 临时文件 → `fsync` → `rename` → 目录 `fsync`；目录 `0700` |
| S3 / MinIO / OSS / COS 等兼容 | `gocloud.dev/blob/s3blob`（路线 6.1 已推荐，底层 aws-sdk-go-v2） | Writer.Close 是提交点；失败时先取消写入 ctx 再 Close。分片上传由 SDK 处理 |
| SFTP | `github.com/pkg/sftp` + `golang.org/x/crypto/ssh` | 写 `.partial` 后 `PosixRename`；**必须校验 known_hosts**，禁止 `InsecureIgnoreHostKey` |
| FTP / FTPS | `github.com/jlaffaye/ftp` | 先 STOR 临时名，再 RNFR/RNTO；默认要求显式 TLS，明文 FTP 需管理员显式允许，界面标出风险 |
| 其余网盘 | 后续评估 rclone 作为库 | 依赖面大，首版不引入 |

数据在离开进程前已经过加密；存储凭据本身按第 8.3 节加密保存。不同后端的持久性和原子性不完全相同，以业务层的“清单 + catalog 事务”作为发布依据。

## 7. 元数据存储（SQLite）

- 驱动：沿用 `modernc.org/sqlite`（纯 Go，免 CGO，便于交叉编译和打包镜像）。
- 连接：沿用 catalog 现有设置 `journal_mode(WAL)`、`busy_timeout(5000)`、`synchronous(FULL)`，写连接 `SetMaxOpenConns(1)`；Web 读多写少，可另开只读连接池，并加上 `foreign_keys(1)`。
- 访问：sqlc 生成查询，goose 嵌入迁移（已定）。sqlc 的 Go/SQLite 支持在官方矩阵中仍是 Beta，模式冻结前需要跑通实际 SQL 生成、迁移和并发事务验证（路线 6.2）。
- 文件布局（待决策）：推荐**单个数据库文件**，`internal/catalog` 继续拥有发布账本表，Web 控制面表使用独立的 goose 版本表（落地前核实 goose v3.26 Provider 自定义版本表的 API），这样运行记录与备份发布可以在同一事务中关联。备选方案是拆成 `catalog.sqlite` 与 `web.sqlite` 两个文件，代价是跨库无事务，需要按 backup ID 对账。
- 现有 catalog 对 state 目录加 flock 独占锁，Web 服务即为该目录的唯一所有者，运行期间 CLI 不能同时操作同一 state，这与路线 6.3 一致。

首版控制面表（示意）：

```text
users(id, username UNIQUE, password_hash, role, disabled, created_at, updated_at)
sessions(token PK, data, expiry)                       -- scs sqlite3store 规定的结构
sources(id, name, engine, host, port, socket, db, username,
        secret_ciphertext, tls_mode, tls_ca, created_by, created_at)
storages(id, name, kind, config_json, secret_ciphertext, created_at)
policies(id, name, source_id FK, storage_id FK, kind, cron_expr, timezone,
         compress, encrypt, enabled, next_run_at, created_at)
runs(id, policy_id FK NULL, trigger CHECK IN ('cron','manual'), idempotency_key UNIQUE,
     status, scheduled_at, started_at, finished_at, bytes, backup_id,
     error_class, error_message, cancel_requested, actor_id)
run_logs(run_id FK, seq, ts, level, message, PRIMARY KEY(run_id, seq))
audit_logs(id, ts, actor_id, action, resource_type, resource_id, ip, result, detail_json)
```

## 8. 鉴权、权限与凭据

### 8.1 登录与会话

- **服务端会话，而不是 JWT**：SPA 与 API 同源，由同一个二进制提供。服务端会话可以立即吊销（禁用用户、强制下线），JWT 要实现吊销最终也得维护一张黑名单。推荐 `github.com/alexedwards/scs/v2` + `sqlite3store`（接收普通 `*sql.DB`，可与 modernc 共用），Cookie 设置 `HttpOnly`、`Secure`、`SameSite=Lax`，登录成功后调用 `RenewToken` 防止会话固定攻击，并配置空闲超时。
- 密码哈希：`golang.org/x/crypto/argon2` 的 argon2id（OWASP 首选），参数写入哈希串以便后续升级。
- 初始管理员：Cobra 子命令 `intern-web user create-admin`，比首次访问时的 setup 页面更安全，不存在抢先注册的竞态。

### 8.2 权限

- 首版使用**固定三角色**：`admin`（用户、存储、恢复执行）、`operator`（数据源、策略、手动备份）、`viewer`（只读）。权限常量放在代码中，通过 `RequirePermission` 中间件校验。
- 恢复执行属于高危操作：需要 `admin` 角色，并在请求中**再次输入密码**确认，审计记录完整计划摘要。
- 暂不引入 Casbin；等到出现多项目 ACL 需求（路线 6.3 的 project ID 隔离）时再评估。

### 8.3 目标库凭据

- 数据源密码和存储密钥以 Tink AEAD 加密后存入 `*_ciphertext` 列，AAD 绑定 `表名:行ID:字段`，防止跨行替换；KEK 复用现有独立 KEK 机制（`0600` 文件，或后续接入 KMS），与 SQLite 文件分开存放。
- API 对 secret 字段只写不读，响应中只返回 `has_password: true`；日志、审计、清单中不出现明文。
- 调用官方工具时沿用现有临时凭据文件机制，不经命令行参数传递密码。

## 9. 前端（选型待 #18）

| 方案 | 组成 | 取舍 |

| **A（推荐）** | React + TypeScript + Vite + Ant Design + TanStack Query + React Router | 后台管理类组件（表格、表单、Cron 编辑、步骤确认）齐全，生态和招人面最广 |
| B | Vue 3 + TypeScript + Vite + Element Plus 或 Naive UI | 上手成本低，中文社区资料多 |

无论选哪个方案都推荐：

- 构建产物 `dist/` 通过 `embed.FS` 内嵌进 Go 二进制，单文件部署；开发时 Vite 代理 `/api` 到后端。
- 维护 OpenAPI 3 文档作为接口契约，前端用 `openapi-typescript` 生成类型；后端是否使用 `oapi-codegen` 生成 Gin 服务端接口另行决定。
- 运行进度和日志使用 SSE（`GET /api/v1/runs/{id}/events`），比 WebSocket 简单，单向推送已经够用。

## 10. 目录结构建议

```text
app/web/
├── go.mod                  # module github.com/flyingEirc/Intern/app/web，replace → ../../internal
├── main.go
├── cmd/                    # Cobra：serve、migrate、user create-admin
├── internal/               # Web 私有（Go internal 规则限制外部导入）
│   ├── server/             # http.Server、Gin engine、外层 scs/CSRF 包装、路由注册
│   ├── middleware/         # auth、rbac、audit、requestlog、limit
│   ├── api/                # 按资源划分的 handler：auth、users、sources、storages、policies、runs、backups、audit
│   ├── service/            # 用例编排：校验、权限后调用 internal/*，不写 HTTP 细节
│   ├── store/              # 控制面 sqlc 查询与 goose 迁移
│   ├── dispatch/           # cron 循环、runs 队列、Worker 池、取消、SSE 广播
│   └── render/             # jsonv2 响应与统一错误体
└── frontend/               # SPA 源码；dist/ 由 embed 引入，构建产物不入库
internal/                   # 共享层，新增：
├── pipeline/               # Source/Stage/Sink 接口与 Run
├── storage/                # local、s3、sftp、ftp 的 Sink/Open
├── artifact/               # 已有：抽出流式 writer 构造，供 pipeline 复用
├── backup/                 # 已有：full 改为流式 Source
├── catalog/                # 已有：发布与清理账本
└── schedule/               # 已有：cron 解析；调度循环是否下沉以 CLI 是否复用为准
```

- 是否在 `internal/` 共享取决于 CLI 是否也需要：pipeline、storage、artifact、backup 属于共享层；鉴权、会话、HTTP、控制面表只属于 Web。
- `app/web/go.mod` 在出现第一份真实后端代码时创建，同时加入 `go.work` 和 mise 任务（build/test/lint 范围扩展到 `./app/web/...`），不提前创建空模块。

磁盘布局（示意，权限沿用现有约束）：

```text
/var/lib/intern/state/   0700  intern.sqlite、work-*、清理账本
/srv/intern/backups/     0700  local 存储
/etc/intern/kek.json     0600  独立 KEK，不放入以上两个目录
```
