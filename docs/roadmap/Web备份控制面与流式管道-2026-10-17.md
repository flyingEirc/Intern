# Web 备份控制面与流式管道：XtraBackup 物理链详细方案（2026-10-17）

> **状态：提案，待 [#18](https://github.com/flyingEirc/IotProject/issues/18) 记录决策。** 用户于 2026-10-17 明确：**Web 首版只做 Percona XtraBackup 物理备份链**。本文据此展开首版方案，所有“推荐”均未采纳、未实现、未验证。开发顺序与目录职责以 [Web 优先总路线](Web优先与多应用架构-2026-10-17.md) 为准；XtraBackup 准入、链、prepare、keyring、加密压缩与验收门禁以 [备份恢复详细方案](数据库备份与恢复-2026-10-17.md) 第 4、5、7、12 节为准。冲突时以二者为准；范围决定在 #18 记录后再回写对应路线。

## 1. 范围

### 1.1 首版包含

| 能力 | 说明 |
| --- | --- |
| 物理全量 | `xtrabackup --backup --stream=xbstream`，流式经 zstd → Tink AES-128-GCM → 存储 |
| 物理增量 | 基于父备份 `to_lsn` 的页增量，可选 page tracking 加速 |
| 备份链管理 | 链 ID、父子关系、LSN 连续性、来源世代与工具版本校验 |
| 调度 | 每个策略两条 cron：全量 cron + 增量 cron；手动触发；取消 |
| 存储 | local + S3 兼容（首批）；SFTP / FTPS 后置 |
| 隔离恢复 | 选择恢复点 → 计划 → 下载认证解包 → 按链 prepare → 输出到隔离目录 |
| 恢复演练 | 在隔离目录启动临时 mysqld 做只读校验，结果单独记录 |
| 控制面 | 用户 / 会话 / 三角色、数据源与存储凭据加密、运行日志、审计 |

### 1.2 首版明确不包含

- **binlog 归档与 PITR**。路线第 12 节要求物理能力的验收包含“全量 + 至少两个增量 + binlog 实际恢复”，因此首版**不能宣称完整物理 PITR**；界面上 PITR 显示为“不可用：未实现 binlog 归档”。binlog 作为同一条链的下一阶段（第 15 节）。
- Web 中的 mysqldump 逻辑链（CLI 保留现有实现，暂停扩展）。
- 远程 Agent、多实例 / HA、多租户项目隔离。
- 自动切换生产 datadir（`copy-back` 到正在服务的实例）。首版只产出隔离的已 prepare 目录，切换由运维手工完成。
- 非 Linux 源机器；矩阵外的 MySQL / PXB 版本组合。

## 2. 部署模型（XtraBackup 决定的硬约束）

XtraBackup 直接读取 InnoDB 数据文件，**必须能访问源实例的 datadir**，仅有 TCP 连接不够（路线 4.1）。因此首版采用“**一机一控**”：

```text
┌──────────────────────── MySQL 主机（Linux）────────────────────────┐
│  mysqld 8.4.x ──datadir──┐                                         │
│                          │ 读                                      │
│  intern-web（单二进制）   ▼                                         │
│   ├─ Gin API + 内嵌 SPA ──── 浏览器（HTTPS，经反向代理或内置 TLS）  │
│   ├─ 调度器 + Worker ──> xtrabackup / xbstream / mysqld（子进程）   │
│   ├─ SQLite（state 目录 0700）                                      │
│   └─ KEK（独立 0600 文件）                                          │
└──────────────────────────────┬─────────────────────────────────────┘
                               ▼
                    local 目录 / S3 / SFTP（密文）
```

| 形态 | 做法 | 取舍 |
| --- | --- | --- |
| **A. 主机 systemd 服务（推荐首版）** | intern-web 与 mysqld 同机，以有 datadir 读权限的专用系统用户运行（例如加入 `mysql` 组） | 最简单；PXB 与 mysqld 版本可以在同一台机器上对齐 |
| B. 容器 sidecar | 与 MySQL 容器共享 datadir 卷和 socket 卷，UID/GID 与 datadir 属主对齐 | 适合容器化 MySQL；UID 对齐和只读挂载是否可行需要实测 |
| C. 控制面 + Agent（后续） | 控制面集中部署，每台 DB 主机运行 agent，以 gRPC + mTLS 通信 | 适合多台主机；首版只在代码中预留 `Executor` 边界，不实现 |

镜像或安装包如果携带 PXB / MySQL 二进制，需要满足 GPLv2 分发义务（路线第 10 节）。首版推荐**要求主机预装经过矩阵验证的 PXB**，intern-web 启动时校验版本，不自带二进制。

## 3. 版本准入与预检

### 3.1 版本矩阵

- 矩阵以数据形式内嵌（`//go:embed compat.json`），每条记录包含：服务器发行版（MySQL / Percona Server）、服务器版本范围、PXB 版本范围、平台、`verified` 标记和对应的证据 Issue。
- 首批只放 **MySQL 8.4.x + PXB 8.4.0-x / Linux amd64**（路线 4.1 的优先组合）。8.0 已 EOL，不作为默认组合。PXB 9.7 在 2026-10-17 已有官方文档页，但路线检索时只有 rc 版本，GA 状态需要重新核实后才能考虑加入。
- 版本解析使用 `github.com/hashicorp/go-version`，不比较字符串前缀。矩阵外的组合一律拒绝，禁止使用 `--no-server-version-check`。
- 备份时把服务器版本、PXB 版本写入清单；**prepare 使用的 PXB 主次版本必须与备份时一致**，否则拒绝恢复。

### 3.2 数据源预检（创建数据源和每次运行前执行）

| 检查 | 方法 | 失败处理 |
| --- | --- | --- |
| 服务器身份 | `SELECT @@server_uuid, @@version, @@version_comment, @@datadir, @@innodb_page_size` | 记录为来源世代；`server_uuid` 或 datadir 变化时增量拒绝，要求新全量 |
| 版本组合 | 服务器版本 + `xtrabackup --version` 对照矩阵 | 拒绝运行 |
| 账号权限 | `SHOW GRANTS` 解析，并实际查询 `performance_schema.log_status` | 列出缺失项，给出授权模板 |
| datadir 可读 | `os.Stat` + 遍历打开测试（不读内容） | 提示部署形态错误 |
| 非 InnoDB 表 | `information_schema.tables` 中用户库 `engine <> 'InnoDB'` | 警告：这些表每次都全量复制，并需要更强的锁 |
| 表空间加密 | `performance_schema.keyring_component_status`、`information_schema.innodb_tablespaces` 的 encryption 标志 | 已使用加密但未配置 keyring 备份材料时，拒绝启用策略（路线 4.4） |
| 临时空间 | `golang.org/x/sys/unix.Statfs` 检查 state / restore 目录 | 低于阈值时拒绝 |
| page tracking | 查询 `mysql.component` 中 `component_mysqlbackup` | 未安装时提示，可选启用 |

备份账号授权模板（来源：Percona 官方文档，2026-10-17 经 Context7 查询；仍需按实际版本核对）：

```sql
CREATE USER 'intern_bkp'@'localhost' IDENTIFIED BY '<secret>';
GRANT BACKUP_ADMIN, PROCESS, RELOAD, LOCK TABLES, REPLICATION CLIENT ON *.* TO 'intern_bkp'@'localhost';
GRANT SELECT ON performance_schema.log_status TO 'intern_bkp'@'localhost';
GRANT SELECT ON performance_schema.keyring_component_status TO 'intern_bkp'@'localhost';
GRANT SELECT ON performance_schema.replication_group_members TO 'intern_bkp'@'localhost';
```

## 4. 备份流程

### 4.1 全量

```text
xtrabackup --defaults-extra-file=<work>/client.cnf     # 0600 临时凭据，必须是第一个参数
           --backup --stream=xbstream
           --target-dir=<work>/tmp                      # 流式模式下只存放少量临时文件
           --extra-lsndir=<state>/lsn/<backup_id>       # 本地另存 xtrabackup_checkpoints / xtrabackup_info
           --parallel=<N> [--page-tracking] [--throttle=<IOPS>]
   stdout ──> tap(计数/进度) ──> zstd ──> Tink StreamingAEAD ──> tap(密文 SHA-256) ──> Sink
   stderr ──> 有界环形缓冲 + 行解析 ──> 脱敏 ──> run_logs / SSE
```

进程正常退出后：

1. 检查退出码为 0，并且 stderr 末尾出现 `completed OK!`（作为辅助判据，主判据是退出码）。
2. 读取 `extra-lsndir` 中的 `xtrabackup_checkpoints`：要求 `backup_type = full-backuped`，解析 `from_lsn`、`to_lsn`、`last_lsn`。
3. 读取 `xtrabackup_info`（工具版本、服务器版本、binlog 位置等）。**把这些文件的原始字节**连同解析结果写入清单（路线 4.2）。不硬编码各版本都会生成同样的文件，实际生成什么就保存什么。
4. 所有 writer 按顺序 Close 后再提交 Sink → 写认证清单 → SQLite 事务标记 `completed`。

与路线 4.2 的关系：路线推荐首版先落盘完整原生目录，再统一压缩加密，并注明“如改为 xbstream 直传，需要重新验证检查点持久化与失败收尾”。本方案选择直传，因此**第 13 节的验收必须覆盖这两项**。直传的收益是 state 盘只需容纳 lsndir 和少量临时文件，不需要容纳整份备份。

### 4.2 增量

```text
xtrabackup … --backup --stream=xbstream
           --incremental-basedir=<state>/lsn/<parent_id>   # 父备份保存的 lsndir，只含 checkpoints
           --extra-lsndir=<state>/lsn/<backup_id> …
```

- 父备份的 lsndir 只有几 KB，与发布记录一起长期保存在 state 中，并在 SQLite 中保留一份原文。这样增量不需要下载父备份本体。另一种写法是 `--incremental-lsn=<parent.to_lsn>`，效果相同，落地时按实际版本的 `xtrabackup --help` 二选一。
- 增量完成后校验：`backup_type = incremental`，且 `from_lsn == parent.to_lsn`。不满足时不发布。
- 下列情况拒绝增量，要求新的全量：父备份未 completed 或已被清理；`server_uuid` / datadir 变化；服务器或 PXB 主次版本变化；链长度达到 `max_chain_length`；父备份所在存储不可读。
- page tracking：全量和增量都加 `--page-tracking`，避免扫描全部页。它依赖 `component_mysqlbackup` 和 BACKUP_ADMIN；首版作为策略选项，默认关闭，验证后再考虑默认开启。

### 4.3 对生产库的影响控制

| 风险 | 控制手段 |
| --- | --- |
| DDL 阻塞 | PXB 8.x 默认用 `LOCK INSTANCE FOR BACKUP` 阻止备份期间的 DDL；界面提示“备份期间 DDL 会等待”。`--lock-ddl` 的具体取值按版本核实后再暴露 |
| 非 InnoDB 表 | 预检警告；这些表会在锁内复制 |
| IO 压力 | `--throttle`、`--parallel`、zstd 并发度均作为策略参数；可选降低子进程 IO 优先级（`golang.org/x/sys/unix` 设置 ioprio / nice） |
| redo 被覆盖 | 写入高峰期的长备份可能追不上 redo；建议配置 `innodb_redo_log_archive_dirs`，并设置容量上限（路线 4.4） |
| 同机资源争用 | 每台主机默认全局并发 1，同一数据源的全量与增量互斥，同时到期时全量优先 |

### 4.4 制品与对象键

每个备份生成三个对象，按顺序写入，**清单最后写**：

```text
<prefix>/<source_id>/<chain_id>/<seq:04d>-<backup_id>/payload.xbs.zst.tink
<prefix>/<source_id>/<chain_id>/<seq:04d>-<backup_id>/envelope.json     # 加密 keyset 与 AAD（沿用 internal/artifact v1）
<prefix>/<source_id>/<chain_id>/<seq:04d>-<backup_id>/manifest.json     # AEAD 保护：checkpoints 原文、LSN、版本、SHA-256、父 ID
```

清单不存在的目录视为未发布或孤儿，由清理账本回收。真正的发布判据是 SQLite 中的 `completed` 记录，不是对象是否存在。

## 5. 恢复流程

### 5.1 计划（只读，默认动作）

1. 选择恢复点 B，从 catalog 取出链 `full → inc1 → … → B`。
2. 校验：每一环 `from_lsn == 父.to_lsn`、同一 chain_id、同一来源世代；所有对象存在且大小一致；本机 PXB 主次版本与备份时一致；keyring 材料可用（如果需要）。
3. 估算空间：各环展开大小之和 × 安全系数，并对照 `Statfs`。
4. 输出计划：链清单、恢复点 LSN、所需空间、目标目录、风险提示（不会自动替换生产 datadir）。

### 5.2 执行（`admin` 角色 + 二次输入密码确认）

```text
for 每一环 i（按顺序）:
    Sink.Open ──> Tink 解密 ──> zstd 解压 ──> 限长 ──> stdin: xbstream -x -C <restore>/<i> --parallel=N
    以 Go 侧 stdin 拷贝错误为准：读到经过认证的 EOF 才算这一环完整；xbstream 退出码为 0 不代表完整

xtrabackup --prepare --apply-log-only --target-dir=<restore>/0
xtrabackup --prepare --apply-log-only --target-dir=<restore>/0 --incremental-dir=<restore>/1   # 中间各环
xtrabackup --prepare                  --target-dir=<restore>/0 --incremental-dir=<restore>/k   # 最后一环
（只有全量时：xtrabackup --prepare --target-dir=<restore>/0）
```

- 物理恢复**可以安全地流式解包**：解包目标是隔离的 restore 工作目录，不是任何正在运行的 datadir。任何一环认证失败就删除整个工作目录，不进入 prepare。这满足“认证通过之前不写目标”的要求。
- 每次恢复都从不可变的归档重新解包；同一工作目录不重复 prepare（路线 4.3）。
- `--use-memory` 作为恢复参数暴露。
- 最终产物是 `<restore_root>/<restore_id>/data`（已 prepare 的 datadir），属主和权限按配置设置。界面给出 `copy-back` / `move-back` 的手工命令和注意事项：停库、空目录、属主、`auto.cnf`。

### 5.3 恢复演练（验证）

```text
mysqld --no-defaults --datadir=<restore>/data --socket=<restore>/mysqld.sock
       --skip-networking --skip-replica-start --pid-file=… --log-error=…
→ 驱动 ping 就绪 → 只读校验 → mysqladmin shutdown → 记录结果
```

- 校验内容：能够启动；系统表可读；各用户库表数量和行数的统计；对选定表执行 `CHECK TABLE`；用户在策略中配置的只读校验 SQL（例如 `SELECT max(id) FROM orders`），结果与备份时记录的值对比。
- 演练实例与源实例使用同一个 mysqld 二进制；不监听网络、不启动复制。
- 结果写入 `restores.verify_*` 字段。**backup completed 不等于恢复已验证**（路线 7.1），界面分开展示。

## 6. 流式管道 `internal/pipeline`

### 6.1 接口

```go
// Source 把数据推入 w；必须等待外部工具退出，并把工具失败、取消作为错误返回。
type Source interface {
	Run(ctx context.Context, w io.Writer) error
}

// Stage 包装下游 next，返回新的上游 writer；Close 只冲刷本节，不关闭 next。
type Stage func(next io.Writer) (io.WriteCloser, error)

// Sink 是唯一提交点：Commit 前对象不可见；Abort 幂等，可在任意状态调用。
type Sink interface {
	io.Writer
	Commit(ctx context.Context) (Receipt, error)
	Abort() error
}

func Run(ctx context.Context, src Source, stages []Stage, sink Sink) (Receipt, error)
```

`Run` 的语义：从 Sink 反向构建链；`src.Run` 返回后按“上游 → 下游”顺序 Close（计数 → zstd → 加密 → 摘要）；任一错误调用 `sink.Abort()`；全部成功才 `Commit`。ctx 取消导致的 EOF 一律视为失败。

推荐同步 writer 链而不是“每节一个 goroutine + `io.Pipe`”：zstd、Tink、hash 本身就是 writer 包装器，串起来就有背压，关闭顺序确定。只有 SDK 要求 `io.Reader` 的 Sink 才在内部用一个 pipe。Databasus（`vendor/databasus/.../create_backup_uc.go:234-321`）为了回收 pipe 和后台写入用了多个 channel，这正是路线第 8 节指出容易漏掉 Close / 上传错误的写法。

### 6.2 XtraBackup Source 草图

```go
type XtrabackupSource struct {
	Binary, DefaultsFile, TargetDir, LSNDir string
	Parallel                                int
	ParentLSNDir                            string // 为空表示全量
	Stderr                                  io.Writer // 有界 + 脱敏
}

func (s *XtrabackupSource) Run(ctx context.Context, w io.Writer) error {
	args := []string{"--defaults-extra-file=" + s.DefaultsFile, "--backup", "--stream=xbstream",
		"--target-dir=" + s.TargetDir, "--extra-lsndir=" + s.LSNDir, "--parallel=" + strconv.Itoa(s.Parallel)}
	if s.ParentLSNDir != "" {
		args = append(args, "--incremental-basedir="+s.ParentLSNDir)
	}
	cmd := exec.CommandContext(ctx, s.Binary, args...)
	cmd.Stdout, cmd.Stderr = w, s.Stderr
	cmd.Cancel = func() error { return cmd.Process.Signal(syscall.SIGTERM) } // 先温和终止
	cmd.WaitDelay = 30 * time.Second                                         // 超时后由 os/exec 强杀并关闭管道
	configureProcess(cmd) // 复用 internal/backup/process_linux.go：Setpgid + Pdeathsig
	return cmd.Run()
}
```

- `cmd.Stdout` 是普通 writer 时，os/exec 内部拷贝；下游写失败会结束拷贝并关闭读端，子进程随后收到 EPIPE。Pipeline 同时在出错时 cancel ctx，保证进程尽快退出、错误分类一致。落地时用故障注入测试验证这一点。
- 凭据通过 `--defaults-extra-file` 临时文件传递（沿用现有 `internal/backup` 的凭据文件机制），不放在命令行参数里。

## 7. 调度与执行

- **策略**：每个策略包含 `full_cron`、`incremental_cron`、`timezone`、`max_chain_length`、`storage_id` 和性能参数。前端提交规范化的表达式；后端用 `cron.ParseStandard` 校验，并提供 `POST /api/v1/schedules/preview` 返回未来 5 次触发时间。
- **调度器**：`robfig/cron/v3`（路线已定，v3.0.1 自 2020 年未发版，但只用它解析表达式、计算 `Next`）。触发循环自建，以 SQLite 的 `next_full_at` / `next_incremental_at` 为准。`go-co-op/gocron/v2`（v2.22.0）更活跃，但任务状态在内存中，仍需自建持久化，因此不作首选。
- **统一队列**：cron 与手动触发都向 `runs` 插入记录，幂等键为 `policy_id:kind:scheduled_at`（手动触发使用 `Idempotency-Key` 请求头），然后由 Worker 用 `UPDATE … RETURNING` 认领。手动触发接口返回 `202 {run_id}`。
- **规则**：同时到期时全量优先；错过的触发合并为一次；同一数据源串行；主机全局并发默认 1；恢复工作目录排他。
- **启动恢复**：遗留的 `running` 运行标记为 `failed(interrupted)`，进程组残留由 Pdeathsig 保证退出，孤儿对象交给清理账本。
- **取消**：写入 `cancel_requested` 并调用该运行的 `CancelFunc`，管道按失败语义收尾。
- 状态沿用路线 7.1：`queued → running → finalizing → completed`，异常进入 `failed / canceled`。

## 8. 存储与保留

| 后端 | 推荐库 | 提交语义与注意点 |
| --- | --- | --- |
| local | 现有 `internal/fsutil` | 临时文件 → fsync → rename → 目录 fsync；目录 0700 |
| S3 / MinIO / OSS / COS 等兼容 | `gocloud.dev/blob/s3blob`（底层 aws-sdk-go-v2） | Writer.Close 是提交点；失败时先取消写入 ctx 再 Close；分片上传由 SDK 处理 |
| SFTP（后置） | `github.com/pkg/sftp` + `golang.org/x/crypto/ssh` | 写 `.partial` 后 `PosixRename`；必须校验 known_hosts |
| FTPS（后置） | `github.com/jlaffaye/ftp` | 先 STOR 临时名，再 RNFR/RNTO；默认要求显式 TLS |

多个目的地不用 `io.MultiWriter` 扇出：每个策略写一个主存储，再由 `replicate` 运行把密文原样复制到副存储，并核对 SHA-256。

**保留以整条链为单位**（路线 7.3）：保留最近 N 条完整链，或 D 天内的链；只有在比它新的完整链已经 completed 后，旧链才能整体进入 `pending_deletions`；永远不删除链的中间环；被恢复引用的链加 pin。首版先实现“只读展示 + 手动删除整条链”，自动保留放在后续阶段。

## 9. 控制面：鉴权、权限、凭据、日志

| 关注点 | 方案 |
| --- | --- |
| 会话 | `scs/v2` 服务端会话，`LoadAndSave` 包住 Gin engine。**Store 用 sqlc 自行实现**（接口只有 Find / Commit / Delete）：官方 `sqlite3store` 的生产代码只依赖 `database/sql`，但它的 go.mod 会把 CGO 的 `mattn/go-sqlite3` 带进依赖图，而且自有迁移更容易纳入 goose |
| Cookie | `HttpOnly`、`Secure`、`SameSite=Lax`；登录后 `RenewToken`；空闲超时 + 绝对超时 |
| 为什么不用 JWT | 同源 SPA；服务端会话可以立即吊销 |
| 密码 | `golang.org/x/crypto/argon2` 的 argon2id，参数编码进哈希串 |
| CSRF | 标准库 `http.CrossOriginProtection`（Go 1.25+），包在 Gin 外层 |
| 登录限流 | `golang.org/x/time/rate`，按 IP + 用户名 |
| 初始管理员 | Cobra 子命令 `intern-web user create-admin` |
| 权限 | 固定三角色：`admin`（用户、存储、恢复执行、删除链）、`operator`（数据源、策略、手动备份）、`viewer`（只读）；`RequirePermission` 中间件。暂不引入 Casbin |
| 凭据 | 数据源密码、S3/SFTP 密钥用 Tink AEAD 加密后存入 `*_ciphertext`，AAD 为 `表:行ID:字段`；KEK 独立存放；API 只写不读，响应中返回 `has_secret: true` |
| 审计 | Gin 中间件：变更类请求完成后写 `audit_logs`，不记录 secret；cron 运行以 `system` 作为操作者，通过运行钩子写入 |
| 任务日志 | 带 `run_id` 的 slog Handler 批量写 `run_logs`，同时广播给 SSE；xtrabackup 的 stderr 逐行脱敏后写入，单次运行设上限 |
| 指标与健康 | `prometheus/client_golang`：最近成功时间、耗时、字节数、失败次数（按数据源）；`/healthz`、`/readyz` |
| JSON | 自有 `render.JSON`，使用 `encoding/json/v2` 编码后经 `c.Data` 输出（路线 6.1 的 Gin / jsonv2 陷阱） |

不适合做成 Gin 中间件的：通知、指标、复制、保留清理、任务日志。cron 触发的运行不经过 HTTP，这些放在运行生命周期事件（`OnRunStarted` / `OnProgress` / `OnRunFinished`）中处理。

明确不引入：Databasus 的 GORM 和自研加密容器；XtraBackup 自带的 `--encrypt`、`--compress` 与 xbcloud。后三者与项目方案的对比如下（依据：Percona 官方文档，2026-10-18 经 Context7 查询；PXB 8.4 源码 `storage/innobase/xtrabackup/src/xbcrypt_common.cc`）：

| 维度 | XtraBackup 自带 | Intern 方案 |
| --- | --- | --- |
| 加密模式 | `--encrypt=AES128/192/256`，源码固定为 **AES-CTR** | Tink `AES128GCMHKDF1MB`，AES-128-GCM 分段流 |
| 防篡改 | 没有认证标签；每块只附一个不带密钥、随数据一起加密的明文哈希，只能发现错误密钥或随机损坏，CTR 可以按位改写 | 每段都有 GCM 认证标签 |
| 截断 / 重排 | 每块独立加密，源码中看不到段序号或流结束标记 | 段序号与最后一段标记参与 nonce，读到认证结尾才算完整 |
| 上下文绑定 | 没有 AAD，文件可以跨备份替换 | AAD 绑定项目、来源、制品与 codec（路线 5.3） |
| 密钥 | 原始字符串直接作为 AES 密钥，所有备份共用，没有 key ID 和轮换 | 每个制品随机数据密钥，由 KEK 包装；有 key ID，支持多键轮换 |
| 压缩 | `--compress` 按文件压缩成 `*.zst` / `*.lz4`；恢复前必须单独执行 `--decompress`，依赖系统 zstd / lz4 包，不清理原文件会占用双倍空间 | 整条流 zstd 压缩一次，恢复时在链路中直接解压后进入 `xbstream -x` |
| 上传 | xbcloud 解析**明文** xbstream，按“库/表文件.序号”切成多个 10MB 对象，并行上传、指数退避；没有发布语义，完整性依赖可选的 `--md5`；“加密”指 SSE-C 请求头，属于服务端加密 | 外层密文是一个不透明对象；Sink 提交 / 放弃 + 清单最后写入 + SQLite 发布 |

结论：xbcrypt 能防偷看，但不能证明数据完整、来源正确，也不符合 AES-128-GCM 的约束；内外两层同时开启压缩属于重复压缩；xbcloud 只接受明文流，无法放在外层加密之后，而且对象名会暴露库表结构。PXB 自带方案的主要优势是并行吞吐。若真实压测证明单条 Tink 流是瓶颈，先调 zstd 并发和 S3 分片并行度，再考虑把一个备份拆成多条并行加密流，不退回 xbcrypt。

| 层级 | 内容 |

| 前端 | 关键页面和状态的截图或 MP4（Issue 规范要求） |

真实容器必测场景（在路线第 12 节中，除 binlog 外的部分）：

1. 全量 → DML → 增量 1 → DML → 增量 2；分别恢复到**增量 1**（不是最新）和增量 2，数据与对应时刻的独立快照一致；演练实例能启动并通过校验。
2. 直传特有：xtrabackup 中途被 kill、Sink 上传中断、取消 → 无 completed 记录、lsndir 不被当作有效父备份、孤儿对象进入清理账本。
3. 拒绝路径：缺中间环、错误父备份、`from_lsn` 不连续、错误 KEK、截断或篡改的 payload、PXB 版本不一致、矩阵外版本、加密表空间缺 keyring、空间不足——全部在 prepare 或写目标目录之前拒绝。
4. 提前 rollback：不允许对中间环省略 `--apply-log-only`，用测试固定 prepare 参数序列。
5. 运行规则：同一 `scheduled_at` 只执行一次；重启后合并错过的触发；全量与增量互斥。
