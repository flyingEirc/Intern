决策来源：用户明确要求暂停 CLI 开发、优先把 Web 做好做完，并采用 `app/{web,cli,site}` 与根目录 `internal/`。总追踪 [#15](https://github.com/flyingEirc/IotProject/issues/15)，路线落地 [#16](https://github.com/flyingEirc/IotProject/issues/16)，目录迁移 [#17](https://github.com/flyingEirc/IotProject/issues/17)，下一步 Web 首版定义 [#18](https://github.com/flyingEirc/IotProject/issues/18)。

本文件维护当前总路线、优先级与应用边界；[数据库备份与恢复详细方案](数据库备份与恢复-2026-10-17.md) 继续维护技术选型、能力设计、历史验证和恢复门禁。发生冲突时，本文件对开发顺序、现行目录与职责的明确决定生效，不据此扩大产品支持范围或降低恢复要求。

## 1. 当前优先级与暂停范围

| 对象 | 当前安排 | 完成边界 |
| --- | --- | --- |
| Web | 产品主线，先明确首版范围和交互，再实现、验证并完成交付 | 真实业务闭环、恢复结果、UI/UX 证据和部署验收全部有据，不能仅以页面或 API 完成结项。 |
| internal | 为 Web 和其他应用共享基础组件与业务能力 | 共享备份、恢复、制品、密钥、元数据和调度语义；因 Web 需要而改动时核对 CLI 兼容性。 |
| CLI | 暂停新功能、专属体验扩展和专属发布推进；保留现有实现与必要维护 | 允许目录/接口适配、回归验证及阻断 Web 的共享缺陷修复，不借维护继续扩大 CLI 范围。恢复开发需明确决策。 |
| site | 随目录迁移保留，当前不抢占 Web 主线 | 产品站点不承担备份控制面，后续独立安排。 |
| mobile | 继续保持未实施状态 | 本轮不迁移、不创建模块或新增能力承诺。 |

既有 [CLI #1](https://github.com/flyingEirc/IotProject/issues/1) 与 [容器门禁 #5](https://github.com/flyingEirc/IotProject/issues/5) / #6–#10 不因暂停而关闭。CLI 专属推进暂缓；其中适用于 Web 共享引擎的真实数据库恢复和安全门禁继续有效，复用范围在 #18 明确后关联 Web 实施任务。原工作区实现按用户授权收尾提交，追踪 [当前仓库 #1](https://github.com/flyingEirc/Intern/issues/1) 及子任务 #2–#6；这次收尾不恢复 CLI 新功能主线，真实容器与 CI 结果仍独立验收。

## 2. 目录与 Go 模块

```text
仓库根目录/
├── .github/     # GitHub 模板与 CI
├── .githooks/   # 本地提交检查
├── app/
│   ├── web/       # Web 产品与其后端，当前主线
│   ├── cli/       # CLI 兼容入口，暂停功能扩展
│   └── site/      # 产品站点，与 Web 产品区分
├── internal/     # 根目录共享基础组件和业务能力
├── docs/         # 路线、流程与开发规范
├── go.work
└── mise.toml
```

- 项目内容直接位于 Git 根，与 `.github/` 同级；不再保留额外的 `Intern/` 包装层（[目录修正 #7](https://github.com/flyingEirc/Intern/issues/7)）。执行路径、mise 与 Go 工作区均以仓库根为准。
- `internal/` 承接原 `base/`，保持现有组件职责，不因改名重写业务或预造跨引擎抽象；禁止导入 `app/*` 的应用入口。
- `app/web` 与 `app/cli` 依赖根 `internal/`，应用专属交互和协议留在各自应用；不得复制第二套恢复引擎。
- 共享模块路径为 `github.com/flyingEirc/Intern/internal`，CLI 模块路径为 `github.com/flyingEirc/Intern/app/cli`；CLI 的本地 replace 指向 `../../internal`。模块前缀按用户决定统一为当前仓库身份（[模块路径统一 #8](https://github.com/flyingEirc/Intern/issues/8)）。
- `go.work` 当前只列 `./internal`、`./app/cli` 两个实际模块。`app/web`、`app/site` 当前只有目录占位；出现实际 Go 后端后再创建对应 `go.mod` 并加入工作区。前端是否采用 Go 模块之外的构建入口按选型决定。
- Go `internal` 的导入范围由工具链限制，应用包须保持与共享层相同的上级模块路径范围；不能把共享层当作对外 SDK。依据见 [Go 项目布局](https://go.dev/doc/modules/layout)。
- mise 继续维护工具和任务。当前 build/run 保留现有 CLI 的兼容入口；Web 尚无可运行实现，不把 CLI 换名为 Web 或创建假 Web 命令。Web 入口随真实实现加入。

### 3.1 已确认的内网部署与存储边界（2026-10-18）

用户确认 Web 面向个人或小团队内部内网使用，采用一套 Helm Chart、每个环境一份 values 配置，并将 SQLite 应用元数据与数据库备份按不同业务分别存储。决策落档见 [当前仓库 #9](https://github.com/flyingEirc/Intern/issues/9)，补充 [首版定义 #18](https://github.com/flyingEirc/IotProject/issues/18)，不代表完整首版范围已确定。

- Chart 维护公共模板与默认值，各环境 values 维护镜像、访问入口、资源、存储和 Secret 引用等部署差异。每个环境拥有独立的应用数据、备份仓库与密钥。
- Web 中维护的数据源、备份策略和任务状态属于应用业务数据；Helm 升级不得用部署默认值覆盖已保存的业务配置。具体页面、数据模型与凭据存储方案随首版范围另行确定。
- 应用元数据、备份仓库、任务工作空间和密钥的职责及后续验收统一维护在 [备份恢复详细方案第 6.2.1 节](数据库备份与恢复-2026-10-17.md)。其中 metadata 与 backups 使用独立 PVC；工作目录独立，卷类型待细化；KEK 由独立 Secret 提供。
- 继续遵守单实例 SQLite 与单调度所有者约束。多个 Web 用户不自动扩大为多副本调度或高可用支持；已有 AES-128-GCM、Tink、Zstandard 和恢复门禁保持有效。
- Helm 安装、升级、Pod 重建及应用卸载后的重新安装，需要验证配置与持久化数据的保留、密钥延续、任务中断处理和真实恢复。具体保留机制不能只凭模板存在宣称有效。

> **已确认、待落档（2026-10-18）**：用户确认首版部署为非 K8s 的 Docker 单宿主机——被备份的 MySQL 为带持久卷的 Docker 服务，Intern 容器在同一宿主机共享 datadir 卷；Helm / K8s 改为后续形态。备份先写本地仓库并发布，再复制到运维统一的 FTP 备份服务器（先以内网明文 FTP 验证，随后 FTPS）；恢复结果导出到宿主机目录。写入 #9 后改写本节 Helm 表述；metadata、仓库、工作根与密钥分离及单实例约束不变。详见 [Web 备份控制面与流式管道](Web备份控制面与流式管道-2026-10-17.md) 第 0、2、8 节。

本轮只完成设计落档；尚无 Web 服务、Helm Chart、独立工作根接口或 Kubernetes 验收。Chart 目录、values 字段、namespace 规则、入口/TLS、更新策略、StorageClass、工作卷类型和 Secret 文件适配方式仍待实施设计；前端、鉴权与页面范围继续由首版定义推进。既有 CLI 配置、工作路径及历史验证不因本节自动改变。

## 4. 继承的技术与安全要求

Go、Cobra、Gin、sqlc、goose、slog、Viper、jsonv2 的既有边界继续有效。Web 前端栈没有在本轮选定；既有 SQLite 单机模式不能自动外推多实例部署能力。

AES-128-GCM、Zstandard、独立密钥、受控工作目录、完整认证、隔离恢复、连续水位及失败语义继续遵循详细方案与 [质量规范](../guide/quality.md)。物理备份、S3、任意时间 PITR 或新数据库只有在明确实施并通过相应验收后才能宣称支持。
