## 2. 目录与 Go 模块

```text
仓库根目录/
├── .github/     # GitHub 模板与 CI
├── .githooks/   # 本地提交检查
├── app/
│   ├── web/       # Web 产品与其后端，当前主线
│   ├── cli/       # CLI 兼容入口，暂停功能扩展
│   └── site/      # 产品站点，与 Web 产品区分
├── internal/     # 根目录共享基础组件和业务能力
├── docs/         # 路线、流程与开发规范
├── go.work
└── mise.toml
```

- 项目内容直接位于 Git 根，与 `.github/` 同级；不再保留额外的 `Intern/` 包装层（[目录修正 #7](https://github.com/flyingEirc/Intern/issues/7)）。执行路径、mise 与 Go 工作区均以仓库根为准。
- `internal/` 承接原 `base/`，保持现有组件职责，不因改名重写业务或预造跨引擎抽象；禁止导入 `app/*` 的应用入口。
- `app/web` 与 `app/cli` 依赖根 `internal/`，应用专属交互和协议留在各自应用；不得复制第二套恢复引擎。
- 共享模块路径为 `github.com/flyingEirc/Intern/internal`，CLI 模块路径为 `github.com/flyingEirc/Intern/app/cli`，Web 模块路径为 `github.com/flyingEirc/Intern/app/web`；CLI 与 Web 的本地 replace 均指向 `../../internal`。模块前缀按用户决定统一为当前仓库身份（[模块路径统一 #8](https://github.com/flyingEirc/Intern/issues/8)）。
- `go.work` 列出 `./internal`、`./app/cli`、`./app/web` 三个实际模块；`app/web/go.mod` 随阶段 B 的 W1（[#22](https://github.com/flyingEirc/Intern/issues/22)）创建并加入工作区，`app/site` 仍只有目录占位。前端工程位于 `app/web/frontend`（F1 [#54](https://github.com/flyingEirc/Intern/issues/54)）：包管理器与运行时为 Bun（版本固定在 mise），构建产物是 Next.js 静态导出，只在带 `webui` 构建标签的 `intern-web` 中内嵌（`mise run build` 与 Web 镜像使用该标签）；不带标签的 Go 构建、测试与 lint 不依赖 Bun，也不提供页面。
- Go `internal` 的导入范围由工具链限制，应用包须保持与共享层相同的上级模块路径范围；不能把共享层当作对外 SDK。依据见 [Go 项目布局](https://go.dev/doc/modules/layout)。
- mise 继续维护工具和任务。`build` 同时产出 CLI `bin/intern` 与 Web 后端 `bin/intern-web`，`run` 保留 CLI 兼容入口；test / check / lint / fmt / generate 与 CI 的 Go 范围覆盖 `./app/web/...`（[#22](https://github.com/flyingEirc/Intern/issues/22)）。不把 CLI 换名为 Web。

### 3.1 已确认的首版决策（2026-10-17 / 2026-10-18）

决策原文与来源见[控制面方案第 0 节](Web备份控制面与流式管道-2026-10-17.md)，追踪 [#11](https://github.com/flyingEirc/Intern/issues/11)；存储职责的落档 [#9](https://github.com/flyingEirc/Intern/issues/9) 继续有效，其中的 Helm 部署表述已由 Docker 单宿主机决策替代为后续形态。

- **范围**：首版只做 Percona XtraBackup 物理链（全量 + 页增量、链管理、调度、隔离恢复、恢复演练）；Web 不做 mysqldump 逻辑链；binlog 归档与物理 PITR 排在首版之后（N1），界面显示不可用。首批矩阵 MySQL 8.4.x + PXB 8.4 / Linux amd64。
- **用户与部署**：个人或小团队内部内网。首版为非 K8s 的 Docker 单宿主机——被备份的 MySQL 是带持久卷的 Docker 服务，Intern 容器在同一宿主机共享其 datadir 卷，不需要执行 agent。Helm / K8s 与跨主机 agent 为后续形态（N3）。
- **存储分离（首版历史决定）**：metadata（SQLite 单文件）、本地备份仓库、任务工作根与 KEK 分开存放；Docker 下分别为命名卷 `intern-metadata` / `intern-backups` / `intern-work` 与 Compose file secret，对应关系见控制面方案第 2.3 节，职责与验收见详细方案第 6.2.1 节。部署参数放环境变量或配置文件；首版数据源、策略和仓库配置等业务数据只存在 SQLite 中，升级镜像不得覆盖。2026-11-09 下一阶段决定用 PG 替代 Web 控制面 SQLite（第 3.2 节），但目录分离、载荷与密钥边界继续有效。
- **备份仓库**：先写本地仓库并发布（即 completed），再把密文原样复制到运维统一的 FTP 服务器并校验；先以内网明文 FTP 验证，随后接入 FTPS，两者都保留。
- **恢复产物**：隔离解包、按链 prepare 后导出到宿主机目录，不自动替换生产 datadir。
- **前端**：2026-10-18 确认的 React + TypeScript + Vite + Ant Design + TanStack Query 已由 2026-11-06 的用户决定**替代**（[#19](https://github.com/flyingEirc/Intern/issues/19)、F1 [#54](https://github.com/flyingEirc/Intern/issues/54)）：Next.js + TypeScript（`bun create next-app@latest` 默认选项）、Bun、Biome（lint/format 与 CI）、shadcn/ui 的 Base UI 底座（缺失组件先搜索开源实现）、Vitest、agent-browser 端到端、TanStack Query、Zod，接口类型、fetch SDK、Query 选项与 Zod 模式由 `@hey-api/openapi-ts` 从 OpenAPI 契约生成。Next.js 以静态导出交付，经 embed 由 `app/web` 同源提供，镜像不引入 Node 运行时；因此不使用 SSR、Server Actions、rewrites 等需要服务端的特性，create-next-app 默认开启的 Cache Components（PPR）与静态导出不兼容而关闭。精确版本见 F1 #54 与 `app/web/frontend/package.json`。2026-10-18 至 11-06 前端暂缓（[#18](https://github.com/flyingEirc/Intern/issues/18)）。
- **后端优先与接口契约**：先完成后端；对前端暴露的接口以仓库内版本化的 OpenAPI 文档为唯一契约（`/api/v1`），由后端维护并用测试校验实现一致，生成 / 校验工具在 W1 决定。后端阶段以 API 测试验收，UI/UX 证据移到前端阶段 F。
- **运行约束（首版历史决定）**：首版遵守单实例 SQLite 与单调度所有者；多个 Web 用户不自动扩大为多副本调度或高可用支持；已有 AES-128-GCM、Tink、Zstandard 和恢复门禁保持有效。下一阶段改用 PG 数据库级锁延续单调度所有者语义，仍不承诺 HA。
- **V1 内网实测取消（2026-11-05）**：不再对用户运维的 FTP 服务器做内网实测（含 V1-A2 内网 FTPS）；FTP/FTPS 改由每次涉及代码或配置的合并前手动运行、main 推送与每日定时运行的真实容器 CI 以固定 Pure-FTPd 1.0.54 夹具验证，非夹具服务器由运维自测。决策见[控制面方案第 0 节](Web备份控制面与流式管道-2026-10-17.md)。

### 3.2 下一阶段决定（2026-11-09，待实施验收）

本节替代第 3.1 节及其他文档中 Web 的 SQLite 单文件控制面和命令行首次管理员方案。PG 入口、浏览器 setup 与业务策略默认值已提交 PR #90；2026-11-10 的原生开发基线 `b45a711` 已通过 D1、W4、既有 CLI/Web 容器与 fast 门禁。完整旧库升级业务闭环、非默认历史调优浏览器编辑、后续最终 head 的 full/UI 与全部独立复验仍待完成，不能把基线绿色写成整体验收通过。第 5 节历史候选、原 SQLite 运维记录与既有 CLI 验证保留原日期和适用范围。

- **Web 唯一元数据库为 PostgreSQL**：覆盖用户、会话、审计、源、仓库、策略、运行、恢复、物理链、检查点、副本与清理账本，包括 `internal/physical/store` 和 `internal/replication` 被 Web 使用的持久层。不得只迁移用户而让业务仍写 SQLite。CLI 既有 SQLite 仅保留必要兼容，共享恢复引擎不复制。备份载荷仍在本地/FTP/FTPS 仓库，工作文件与 KEK 均不进入 PG；凭据继续以现有加密封装存储。
- **升级必须保留历史**：提供从旧 SQLite 到 PG 的受控升级，覆盖用户、策略、运行、备份链、副本、恢复索引和清理责任；失败不得删除旧库或静默以空 PG 启动。迁移是运维升级步骤，不是日常命令行建管理员。单调度所有者由 PG 数据库级锁保护，同一 PG 即使使用不同 metadata-dir 也不能同时消费任务。已批准锁与数据共用唯一物理连接、断链后禁止驱动自动重连，Store 永久失败并取消 serve/运行工具；不由此宣称 HA。
- **浏览器首次初始化**：提供匿名只读状态和一次性创建首位管理员接口；未初始化时 login 引导到 setup，成功后进入正常登录或控制台。首管、完成标记和成功审计在同一事务提交，并发请求仅一个成功，审计失败全部回滚；完成、重启、禁用全部用户或导入既有用户后均不可重新匿名创建。明确决定删除 Web 生产命令 `intern-web user create-admin` 及仅服务它的 `store.OpenCurrent`，消除并行引导、独立写连接和绕过一次性 setup 的风险；`app/cli` 的既有逻辑备份兼容不是 Web 首管入口。恢复账号走已认证用户管理或明确运维恢复流程，不增加新后门。上述删除待实施验收，不提供任意自助注册。
- **业务化保护策略**：主要输入为保护目标、数据源、存储、时间安排与启用。链长、工具并行、限速、压缩、page tracking 等默认值在服务端唯一维护，前端不定义第二套；只编辑业务字段不得静默覆盖历史调优值，若统一清理需明确迁移。调度预览继续复用后端同一个调度器。
- **业务术语与界面**：以 Backup management console / Data protection console（备份/数据保护控制台）、protection policy builder（保护策略配置）、schedule builder（时间安排）、recovery wizard（恢复向导）、data table（数据表格）为调研方向。核实成熟开源组件的维护、许可证、固定版本与 Base UI 兼容性，再按已锁 Next.js 静态导出、shadcn/Base UI 与语义令牌统一导航、表单、表格、状态和响应式视觉；不另建第二设计体系。
- **范围与放行**：不扩展计费、多租户、任意自助注册、HA、K8s、PITR 或自动保留。各子任务锁定逐条可运行验收，实施者完成后交独立验收者；发现成立后由修复者处理，再交原验收者复验。既有物理备份、真实容器矩阵、普通合并门禁与原生 UI 证据不可降低；开发不等待冗长 CI，未完成/未绿仍不得合并或结项。

已实现、待完整独立验收的契约：setup 使用 `GET/POST /api/v1/auth/setup`，操作名 `getSetup` / `createSetup`；创建返回 `201 {user}` 并建立正常会话，完成后返回 `409 setup_completed`，已有任何用户（包括禁用用户）也视为初始化完成。密码、会话、跨源与审计语义沿用原安全边界。

策略默认值由服务端 `store.DefaultPolicyTuning()` 唯一维护：`max_chain_length=7`、`parallel=1`、`throttle=0`、`zstd_level=3`、`page_tracking=false`，沿用现有产品默认并收敛来源；7 限制单条物理链深度，不是业务调度频率上限；1 保守使用工具并行，0 不额外限速，false 不增加 page tracking 前提。`zstd_level=3` 当前只是历史记录值，现有流编码器仍固定并发 1 且未应用 level，不能把默认字段当作编码器已支持该调优的证明。更新只接受业务字段，数据库更新不触碰历史五列，响应可保留只读诊断字段；普通策略界面不展示低层参数面板，包括默认折叠的面板，也不要求用户额外声明采用默认参数。已有自定义 cron 必须无损保留，业务时间构建器提供日/周/月/每小时安排。准确 schema 以 OpenAPI 与生成客户端为准；B2 必须预置非默认历史调优并由浏览器业务编辑后回读，默认值前后相等不算该项通过。

链满行为（#83 决策，待实施验收）：隐藏固定 `max_chain_length=7` 后，不新增业务限制或 UI 警告，沿用既有服务端链满自动轮转。源码依据为 `internal/physical/store/plan.go` 在 `len(backups) >= MaxChainLength` 时返回 `RequiresFull` / `chain_length_reached`；`app/web/internal/dispatch/backup.go` 的 `admissionFailure`、`queueAdmissionFull` 与 `HasActiveFull` 让被拒增量触发一次合并的 `admission` 全量，后续调度继续。该选择保持每周全量 + 每小时增量等业务频率合法、最小改动、不扩自动保留或 PITR，也不把链长暴露为第二套默认值。B3 / G2 必须由 PG 负责人在真实源/仓库上覆盖链满 7 → 1 个合并全量 → 继续增量与副本，不能仅凭源码断言。
